# Hero code policies

- Each domain is a module with explicit ownership. Trait files contain only data models and defaults. Define actions as arrow-function properties in each action set. Domain actions own commands that create, attach, remove, destroy, or transition world state. Systems advance existing state and invoke actions for discrete commands. Renderers own mounted resources and send commands through actions. Depend on another domain through its traits, actions, content, and utils, and share shader contracts through its materials; renderers also register with the loading domain's preparation and take its fonts. Do not import another domain's systems or renderers: when a domain needs another's behavior, the owner publishes the result as state. The director domain owns actor choreography and its declared script, and the viewport domain publishes the camera and floor metrics every domain reads. The sequence domain owns only cue scheduling and dispatch. Declare timed or event-triggered commands in the script instead of embedding beat timing in systems. Keep the source root to what is the whole app's: `main.tsx`, `app.tsx`, `frameloop.ts`, `world.ts`, `actions.ts`, the page's `styles.css`, shared traits, and generic helpers in `utils.ts`; anything with an owner belongs in its domain. Root `app.tsx` owns Canvas and providers and composes every domain's renderer and the post pass. Root `world.ts` owns the shared application world. Root `frameloop.ts` connects the renderer clock to simulation. The application root composes the domain action sets. Root actions combine the domain action sets for application code. Keep domain actions directly importable when names collide or a consumer needs only one domain. All domains share one Koota world, and simulation must run without React. Add only the files a domain needs.
- Keep behavior with its domain owner. Simulation belongs in systems, commands in actions, and mounted resources in renderers regardless of function size. Keep named modules such as `content.ts` and `samples.ts` at the domain root. Combine related uniforms and material builders in `materials.ts`. Inline small single-use helpers and trivial factories that only return object literals. Reserve `utils.ts` for compact calculations and conversions with explicit inputs and caller-owned outputs. Keep simulation independent of rendering imports.
- Prefer tests of observable features and common user stories. Add edge cases only for important behavior or meaningful regressions. Keep internal tests only where a difficult case cannot be covered reliably through observable behavior.
- Treat comments as documentation. Keep them concise and explain the algorithm or feature. Avoid change history, semicolons, and em dashes.
- Prefer inline values for local tuning. Before adding a top-level constant, check whether it needs a separate name or lifetime. Keep shared contracts and retained resources named when inlining would duplicate a coupled value or allocate during playback.
- Prefer SoA trait schemas for scalar state, with per-field factories for owned buffers and records. Keep AoS for opaque resources whose identity must remain stable. SoA `get()` returns a snapshot, so publish scalar changes with `set` or `updateEach` and sample live scalars inside frame callbacks.
- Use Koota `query(...).updateEach` for query mutations. Select only traits the callback owns for writeback so it cannot overwrite another action's updates.
- List every simulation and view system directly in root `frameloop.ts` in execution order. Keep each system focused on one responsibility in its domain and avoid a nested application tick that hides the order. Renderers prepare resources and attach them through domain actions as view traits, then detach them before disposal. View systems query those traits so unmounted views receive no updates. Visibility is separate from mounting because hidden views must still prepare before playback.
- Put a blank line before and after hooks with callback bodies, loops, branches, and other code blocks when adjacent statements exist. Keep comments attached to their blocks, keep related `else` and `catch` clauses together, and separate returns from preceding work. Do not pad the inside of enclosing braces.
