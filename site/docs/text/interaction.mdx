## From a pointer to a caret

```tsx
import type { GlyphCaret } from '@pmndrs/glyph';
import { Text } from '@pmndrs/glyph/react';
import type { Text as ThreeText } from '@pmndrs/glyph/three';
import type { msdf } from '@pmndrs/glyph/raster/msdf';
import { useRef, useState } from 'react';

const ref = useRef<ThreeText<typeof msdf>>(null);
const [cursor, setCursor] = useState<GlyphCaret | undefined>(undefined);

<Text
  ref={ref}
  font={Inter}
  onPointerDown={(event) => {
    const target = ref.current;
    if (target === null) return;
    const local = target.worldToLocal(event.point.clone());
    const caret = target.caretAt(local.x, -local.y); // paragraph space is y-down
    if (caret !== undefined) setCursor(caret);
  }}
>
  Click to place the caret
</Text>;
```

{/*
write
- Question: I have a pointer event; where is the caret?
- Paragraph 1: R3F raycasts the text's draw meshes, so the event carries a world point; bring it into the text's
  local space, flip y, and ask. `caretAt` picks the line whose box contains y (or the nearest line), then the
  nearest cluster edge on that line, comparing leading and trailing edges so a right-to-left glyph resolves to the
  boundary logically before it even though that edge is drawn on its right.
- Paragraph 2: what comes back: `offset` (a UTF-16 cluster boundary), `line`, `leading`, and `rect`, a zero-width
  box the height of the line; draw the caret from `rect` as a child of the text.
- Avoid: explaining raycasting; point at R3F's event docs.

## Selection

```ts
import { Mesh, MeshBasicNodeMaterial, PlaneGeometry } from 'three/webgpu';

const [anchor, focus] = [3, 9];
for (const box of text.selectionRects(anchor, focus) ?? []) {
  const highlight = new Mesh(new PlaneGeometry(box.width, box.height), new MeshBasicNodeMaterial({ color: '#264f78' }));
  highlight.position.set(box.x + box.width / 2, -(box.y + box.height / 2), -0.01);
  text.add(highlight); // a child inherits the text's transform
}
```

{/*
write
- Question: how do I draw a highlight over a range?
- Paragraph 1: one rectangle per line segment, spanning the union of the selected glyphs' advance boxes on that
  line and the full height of the line box — what `Range.getClientRects()` returns for DOM text; a highlight is a
  layout-box artefact, not an ink one. A bidi line whose selected characters are drawn in two places yields two
  rectangles rather than one across the gap.
- Paragraph 2: `start` and `end` may be given in either order; an empty range yields no boxes; non-finite offsets
  throw. Draw the boxes as children of the text so they inherit its transform, just behind the glyphs.
- Shape: two paragraphs.

notes · internals
- `selectionRects` semantics and the bidi split — `glyph-placement.ts:504–545` (docstring `:504–511`, gap closes a run `:534–537`)
- order-insensitive, empty range → `[]`, non-finite throws `RangeError` — `glyph-placement.ts:518–521`

## `undefined` means pending

| State | `caretAt` / `selectionRects` |
| --- | --- |
| never traversed | `undefined` |
| desired change not yet committed | `undefined` |
| renderer rejected the last candidate | `undefined` until a checkpoint succeeds |
| committed | answers |

{/*
write
- Question: why did it return `undefined`?
- Paragraph 1: the queries read a snapshot built from the committed layout and the drawn origins in the retained
  render records, so they can only answer for a revision the renderer accepted. Before the first traversal there is
  no binding; after `set()` the desired revision is ahead of the committed one; after a rejected candidate the
  binding is flagged until a later checkpoint succeeds. `commitState()` reports the same states by name.
- Paragraph 2: measurement is desired-state and never returns `undefined`; do not mix the two in one frame's
  logic, and do not poll — the next traversal after a successful `glyph.shape()` answers.
- Shape: two short paragraphs; the table carries the cases.

notes · internals
- placements only for a committed revision, never after a rejection — `three/text.ts#ThreeRootPublication.#canonicalInspection`
  (`:1343–1357`), `#glyphPlacements` (`:1213–1225`)
- the rejection flag — `three/text.ts:1283–1286` (`rejectShape`), cleared at `:1272–1274` (`acceptShape`)
- `commitState()` — `three/text.ts:756–764`; D-285 (placement queries return `undefined` until a checkpoint realises)
- the snapshot carries drawn origins and names glyphs it could not read — `glyph-placement.ts:137–150` (`incomplete`)
*/}

## An editing loop

```ts
import { Mesh } from 'three/webgpu';

let value = 'Hello';
let cursor = value.length;
const caretMesh = new Mesh();

function onKey(key: string): void {
  value = value.slice(0, cursor) + key + value.slice(cursor);
  text.text = value; // one narrow edit is derived from the assignment
  cursor += key.length;
}

function onFrame(): void {
  const [box] = text.selectionRects(cursor - 1, cursor) ?? []; // the cluster before the cursor, once the frame is accepted
  if (box !== undefined) caretMesh.position.set(box.x + box.width, -(box.y + box.height / 2), 0);
}
```

{/*
write
- Question: how do keystrokes, the engine, and the caret line up in time?
- Paragraph 1: keystroke → assignment (the planner derives one scalar-aligned replace) → the next traversal
  publishes → the frame after that, the caret query answers for the new text. Keep the cursor offset in your own
  state; read placement only to draw.
- Paragraph 2: there is no caret-from-offset call; `caretAt` is point-based. To draw a caret at an offset, take the
  cluster before it from `selectionRects(offset − 1, offset)` and use its trailing edge, or keep the `GlyphCaret`
  the last pointer hit returned.
- Close by pointing at Rich text → Editing for restating styled runs on each keystroke.
- Shape: two paragraphs, one pointer.

- the minimal edit — `engine-encoding.ts#minimalTextMutation` (`:312–335`); assignment is `set({ text })` — `three/text.ts:676–678`
