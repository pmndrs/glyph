## The runtime and a handle

```ts
import { glyph } from '@pmndrs/glyph';
import { ThreeConfig } from '@pmndrs/glyph/three';

await glyph.init();
const three = glyph.handle('main', ThreeConfig);
```

{/*
write
- Question: what do I set up before the first text?
- Paragraph 1: `init()` loads the engine once and returns the same settled promise forever; a handle is one adapter
  with a name that is unique while it lives and reusable after it is disposed. Creating a handle needs no renderer,
  scene, camera, canvas, or device.
- Paragraph 2: R3F does this for you: the first `<Text>` initializes the runtime and creates one default handle
  and one default root per canvas; a `GlyphProvider` is how you pick a different one.
- Shape: two short paragraphs.

notes · internals

## Roots

```ts
const hud = handle('hud'); // idempotent: the same name returns the same live root
hud === handle('hud'); // true
hud.createText({ font: Inter, text: 'HP 100' });
```

| Root | Owns |
| --- | --- |
| the handle itself (anonymous) | one encoder, capacity, compositing, material fallback, one draw object, at most one `Scene` |
| `handle(name)` | the same, independently |

```ts
import { glyph } from '@pmndrs/glyph';
import { defineThreeConfig } from '@pmndrs/glyph/three';

const three = glyph.handle('main', defineThreeConfig({ capacity: { size: 8192, policy: 'chunk' }, compositing: 'independent' }));
three.setCapacity({ size: 16384, policy: 'chunk' });
three.setCompositing('ordered');
```

### Compositing

| Mode | Behaviour |
| --- | --- |
| `ordered` (default) | preserves authored draw order |
| `independent` | lets Rust reorder compatible draws when blending order does not matter |

### Capacity

| Policy | Behaviour |
| --- | --- |
| `grow` | grow retained storage to fit |
| `chunk` (default, 4096) | grow in multiples of `size` |
| `fixed` | keep the last accepted draw while desired text exceeds `size`; `measure()` still answers |

{/*
write
- Question: when do I need a second root, and what does one control?
- Paragraph 1 (under the first code): roots are terminal — a root cannot make another root — and every `Text` is
  created from one. A root discovers its `Scene` from its attached texts; a root that would span two scenes is an
  error, so two scenes use two named roots. Names are stable customization labels you choose, never derived from
  `Scene.uuid`.
- Paragraph 2 (under the second code): capacity and compositing are per root, set at the config for every root the
  handle makes and adjustable per root afterwards; the config also carries `defaultFontFormat`, `transformMode`,
  `allocationMode`, and a renderer-wide fallback `material`.
- Under Compositing: one sentence — `independent` is for many small labels whose blending order does not matter.
- Under Capacity: one sentence — `fixed` bounds by UTF-16 length before shaping; exceeding it is a policy, not an
  error, rechecked every shape, and the previous draw stays visible.
- Avoid: "standalone" versus "group" capacity defaults; at HEAD every Text is on a root and the default is one number.

## Create text

```ts
const label = three.createText({
  font: Inter,
  text: 'Hello world',
  style: { fontSize: 32, lineHeight: 1.2, color: '#ffffff' },
  layout: { wrap: 'word', overflow: 'clip' },
  constraints: { width: { mode: 'at-most', size: 420 } },
});
scene.add(label);
```

## TextGroup

```ts
const title = three.createText({ font: Inter, text: 'Title' });
const body = three.createText({ font: Inter, text: 'Body' });
const panel = three.createTextGroup({ renderOrder: 2, pixelSnapping: true });
panel.add(title, body);
scene.add(panel);
```

{/*
write
- Question: what is a group for, if not batching?
- Paragraph 1: a nestable parent that a `Text` inherits transform, visibility, material, pixel snapping, and render
  order from — the nearest group's value wins. It creates no planner and no publication stream; batching is the
  root's job, and every `Text` on a root already shares it.
- Paragraph 2: a group cannot hold texts from two roots, cannot be cloned or copied, and disposing it does not
  dispose its children. Use groups to organize; use roots to isolate.
- Shape: two paragraphs.

notes · internals
- options — `three/text.ts#TextGroupOptions` (`:84–90`); inheritance walk, nearest group wins —
  `#resolveTextPresentation` (`:1629–1657`)
- `add` validates one root — `three/text.ts:1014–1022`, `:1054–1060`; no clone/copy `:1024–1030`; dispose leaves
  children `:1032–1038`; `textCount` `:986–988`
- errors are attributed to the group ancestors of the failing texts — `three/text.ts:494–503`
- no planner per group — D-307
*/}

## Shape

```ts
import { glyph } from '@pmndrs/glyph';

text.text = 'Updated';
text.style = { ...text.style, color: '#ffd166' };
glyph.shape(); // every dirty root, every live handle, one Wasm batch
renderer.render(scene, camera); // three draws the meshes shape() attached
```

![Two paths through a frame: a semantic change goes through one Wasm batch and a decode-and-commit; a transform-only change syncs matrices without entering Wasm.](/examples/diagrams/frame-paths.svg)

{/*
write
- Question: when does a change become pixels?
- Paragraph 1: `glyph.shape()` stages every dirty root across every live handle and crosses into Wasm once;
  unchanged roots do not enter the batch, and one root may fail without another root's state being touched. Matrix
  and visibility changes take the cheap renderer-local path and never shape.
- Paragraph 2: R3F calls it for you before the host renders; imperative code calls it once per frame or after a
  batch of edits. The root's draw object also calls it during three's matrix traversal, so a forgotten call is a
  late frame, not a blank one. `Text` and `TextGroup` have no publish method.
- Paragraph 3: a rejected shape keeps the last accepted draw and reports on `text.error`, `text.onError`, and
  `commitState()` as `failed` (link Errors).
- Point at the figure: the two paths.
- Shape: three short paragraphs.

notes · internals
- the split-flap scene is 150 one-character texts on one root; each flip is a group rotation with `text.set()` at the midpoint —
  `site/examples/src/scenes/split-flap/scene.tsx`
- `glyph.shape()` — `glyph.ts:94–98`; one `pmndrs_glyph_engine_update_batch` crossing, per-entry status — D-312
- root hooks: `prepareShape` (reconcile members, capacity check) — `three/text.ts:436–448`; `acceptShape` `:451–459`;
  `rejectShape` keeps the last draw and attributes the error `:462–465`
- transform-only path — `three/text.ts#ThreeRoot.#syncTransforms` (`:467–476`); the draw object's matrix traversal
  commits and calls `glyph.shape()` — `#ThreeRootDrawObject` (`:131–148`), `#commitTraversal` (`:478–492`)
- no publish method on `Text`/`TextGroup` — D-312
- error retention — `three/text.ts:918–922`; `commitState()` `:756–764`
- [verify] what R3F calls before render (`useFrame` priority or the draw-root traversal only): read the R3F
  adapter in `react.ts` around the `invalidate` calls before writing "before the host renders"
*/}

## Ownership and disposal

| Call | Effect |
| --- | --- |
| `text.dispose()` | unbinds; releases its font lease |
| `group.dispose()` | removes the parent; does not dispose child texts |
| `root.dispose()` | ends that root's publication stream and GPU resources |
| `handle.dispose()` | disposes its roots; the name becomes reusable |
| `face.dispose()` | releases after every text lease is gone |

{/*
write
- Question: what order do I tear things down in?
- One paragraph: texts, then faces, then roots or the handle; a disposed group's live children can be re-parented;
  the last text leaving a root also ends that root's publication.
- Shape: the table and one paragraph.

notes · internals
- `Text.dispose()` — `three/text.ts:875–881`; `TextGroup.dispose()` — `:1032–1038`; `ThreeRoot.dispose()` — `:290–304`
- the last member leaving a root disposes its publication — `three/text.ts#ThreeRoot.unregister` (`:383–394`)
- handle disposal cascades to roots — `internal/configured-handle.ts:120–150`; name released — `glyph.ts:76–79`
- `FontFace.dispose()` — `font-face.ts:266–280`, `:679–692`
