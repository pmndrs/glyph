{/*
reader
- Has a paragraph and wants one run of it in another colour, font, or material; may be typing into it. Knows what a
  string offset is and has been burned by one; has probably never heard the words "grapheme cluster". Arrives asking
  "how do I bold one word?", should leave able to author a styled document in either API, read the resolved
  runs back, and edit a live paragraph one keystroke at a time without thinking about offsets.

write · intro
- Question: what is a span, and where do its edges come from?
- Say: a paragraph is one shaped unit; a span is a range inside it that overrides font, style, or material and
  inherits the rest. You never write an offset: `txt`/`span` in three.js and nested `<Text>` in React are two
  compilers of one document tree, each derives a boundary where two fragments meet, and each settles that boundary
  onto a grapheme cluster before a frame is built.
- Anchor: "the tree is the document; the offsets are derived, not authored".
- Shape: three sentences, no list.

write · keypoints (pmndrs `<Keypoints>`, four items, one clause each)
- Two ways to author the same document: `txt`/`span` fragments, or nested `<Text>`.
- A span overrides font, style, or material and inherits everything it does not name.
- The cluster rule: a boundary moves forward, a base keeps its style, nothing throws.
- Editing is assignment: one narrow edit per keystroke, runs restated with the text.

notes · internals for the page

## Template tags

```ts
import { txt } from '@pmndrs/glyph';
import { defineTextMaterial, span } from '@pmndrs/glyph/three';

const glowMaterial = defineTextMaterial((context) => context.createDefaultMaterial());
const ok = span({ color: '#4ade80' });                 // a style
const glow = span(glowMaterial, { color: '#ffd166' }); // the /three span also takes one material

three.createText({ font: Inter, text: txt`Status: ${ok`online`} ${glow`●`}` });
```

```ts no-check
import { glyph, txt } from '@pmndrs/glyph';
import { span } from '@pmndrs/glyph/three';
import { msdf } from '@pmndrs/glyph/raster/msdf';

const Mono = glyph.fontFace('/fonts/mono.font.glb', { format: msdf });
await Mono.load();
const code = span(Mono.msdf, { letterSpacing: 0.01 }); // a different font for the run, same format as the paragraph

three.createText({ font: Inter, text: txt`in ${code`us-east-1`}` });
```

{/*
write
- Question: how do I mark a run without counting characters?
- Paragraph 1: `txt` is a template tag that concatenates strings and fragments; `span(...)` builds a tag that wraps
  its own template in one set of overrides. A span states only what it changes: pass a style object, a font, a
  material, or several; what you leave out is inherited from the paragraph. Nesting is allowed; a fragment inside a
  fragment composes over it.
- Paragraph 2: the boundaries are derived at each join as text is appended, then settled onto the cluster grid of
  the finished text (link to The cluster rule). The result is a frozen `{ text, spans }` you hand to `text`.
- Point at: the second block is the font case; say plainly it is the canonical form and that the tree is catching
  up (do not explain the loader path).
- Avoid: showing the resolved `spans` array here; that is Reading the result.
- Shape: two short paragraphs; the code carries the syntax.

- `span(...styles)` → `UnboundSpanTag`; `span(font, ...formats)` → `SpanTag<Technique>` — `formatted-text.ts:121–132`;
  the `/three` overload accepts one `ThreeTextMaterial` beside styles and a font, two throw

## Nested Text

```tsx
import { Text } from '@pmndrs/glyph/react';
import { useMsdf } from '@pmndrs/glyph/react/msdf';

const mono = useMsdf('/fonts/mono.font.glb'); // a nested font must be a loaded Font

<Text font={Inter}>
  Status: <Text style={{ color: '#4ade80' }}>online</Text> in <Text font={mono}>us-east-1</Text>
</Text>;
```

{/*
write
- Question: what is a `<Text>` inside a `<Text>`?
- Paragraph 1: an inline run, not an object. It creates no `Object3D`, has no transform, and accepts only
  `children`, `font`, `style`, and `material`; every other prop is a box property and is rejected by name when the
  tree is flattened. It inherits the paragraph's font, style, and material and overrides what it states.
- Paragraph 2: the outer `<Text>` needs a font; a nested one may carry a loaded font from a hook. The tree
  flattens to the same `{ text, spans }` the template tags produce, with the same join rule.
- Avoid: explaining Suspense here; link React components.
- Shape: two short paragraphs.

notes · internals
- flatten: strings and numbers append, arrays recurse, a nested `Text` element opens a span over its children —
  `react.ts#flattenText` (`:758–791`); non-Text children throw (`:777–778`)
- inline props are the closed set `children`, `font`, `material`, `style`; anything else throws
  `nested R3F Text cannot use the box property …` — `react.ts#INLINE_TEXT_PROPERTIES` (`:820`), `#assertInlineTextProperties` (`:822–826`)
- inheritance: a nested style merges over the inherited one; font and material fall back to the parent's —
  `react.ts#inlineProperties` (`:804–818`)
- a nested `font` must be a loaded `Font`; a face or family string throws, and the message says to load it through a
  hook first — `react.ts#loadedInlineProperties` (`:793–802`, throw at `:797–800`)

- the same join rule as `compose` — `react.ts:748–757` (docstring), `:790`
- rich-text scene: nested colour, font, style, and material runs in one paragraph — `site/examples/src/scenes/rich-text/scene.tsx`
*/}

## What a span may override

| Field | Effect |
| --- | --- |
| `font` | a different loaded font for the run; its format is validated with the paragraph's when effects are checked |
| `style` | any `TextStyle` member; the rest inherits |
| `material` | a `defineTextMaterial` factory; span → text → group → root → config precedence |

{/*
write
- Question: what can a run change, and what wins when two things say so?
- One sentence per row, in plain words. Font: a run can select another loaded font; today that is a font in the
  paragraph's own format, and a span that carries an outline or shadow is checked against that font's format, not
  the paragraph's. Style: any member of `TextStyle`, merged over the inherited style. Material: the nearest
  material wins, from the span outward to the handle's config.
- Close with one sentence pointing at Materials for the material precedence and Raster formats for mixing formats.
- Avoid: the word "stack"; fallback stacks are not documented until the loader path settles.
- Shape: three sentences and a pointer.

notes · internals
- the span record — `three/text.ts#TextSpan` (`:56–57`): `ParagraphSpan` minus `font` plus `font?: FontSelection`, `material?: ThreeTextMaterial`
- effects validated per span against the span's own font, else the paragraph's —
  `three/text.ts#normalizeDesired` (`:1457–1472`, `assertTextEffectsSupported`)
- material precedence: `desired.material ?? presentation.material ?? root.material` — `three/text.ts#coreTextState`
  (`:1377–1381`); the config-level fallback after that — `three/handle.ts#ThreeSchema.material` (`:121–122`),
  `#ThreeConfigOptions.material` (`:97–98`)
- a span material becomes its own material binding — `three/text.ts:1382–1395`
- [verify] whether a span font may be a different format from the paragraph's at HEAD: `normalizeDesired` only unions
  the techniques for effect checks (`three/text.ts:1457–1464`); the fact sheet's "in the paragraph's raster format" claim needs a
  test with an MSDF paragraph and a Slug span before it is stated

## The cluster rule

```ts
import { span, txt } from '@pmndrs/glyph';

txt`a${span({ color: '#ff0000' })`́b`}`;
// text  'áb' — the base and the combining acute fused into one cluster spanning [0, 2)
// spans [{ start: 2, end: 3, … }] — the fused cluster keeps the style of its base, which is plain
```

{/*
write
- Question: what happens when a style boundary lands inside a character?
- Open with an `> [!IMPORTANT]` callout, three sentences: a cluster takes the style of its base; every span boundary
  moves forward to the end of the cluster containing it, so a mark that attaches to a base follows the base; nothing
  throws.
- Paragraph after the code: why forward and not backward — backward would take a style away from a base you styled
  and hand the cluster to a mark that merely attached to it; both edges move the same way so two adjacent spans
  stay adjacent instead of overlapping. A span left with no cluster of its own collapses to an empty `[n, n)` and is
  kept, so entries still line up with what you authored; an empty span states nothing.
- Closing sentence: an inverted or out-of-range span is a different fault and throws from construction or `set()`;
  the cluster rule never hides it by clamping.
- Anchor: "the mark goes where its letter goes".
- Shape: callout, code, one paragraph, one sentence.

notes · internals
- the rule and its reasons — `internal/graphemes.ts#alignRangesToClusters` (`:42–91`; forward policy `:50–56`, empty
  ranges kept `:57–61`, out-of-range left alone `:63–65`); D-265
- one implementation for both compilers and the backstop — `internal/graphemes.ts#resolveRangesToClusters` (`:93–126`);
  `formatted-text.ts#alignSpansToClusters` (`:64–69`) is the backstop for the untyped array
- ill-formed UTF-16 is returned untouched for the engine to reject — `internal/graphemes.ts:124–125`; unpaired
  surrogates throw at `Text` — `three/text.ts#assertPairedSurrogates` (`:1560–1572`)
- inverted or out-of-range spans throw `RangeError` — `three/text.ts#assertRange` (`:1524–1532`); partial overlap
  throws `spans must nest or be disjoint` — `#assertSpansNest` (`:1534–1558`)
- the segmenter is the package's own UAX #29 tables, never `Intl.Segmenter` — `internal/graphemes.ts#findGraphemeBoundaries` (`:17`); D-265, D-320
- the worked example and its expected offsets — `.agents/docs/planning/three-api.md:230–234`
- `alignSpansToClusters` is not exported from the root or `/three` at codex `1dc580a87` (grep of `index.ts` and
  `three.ts` finds none); D-265 calls it "the exported function a caller checks its own offsets with". Do not tell the
  reader to call it until it is
*/}

## Editing

```ts
import { txt } from '@pmndrs/glyph';
import { span } from '@pmndrs/glyph/three';

const ok = span({ color: '#4ade80' });
let value = 'Status: online';

value += '!';
text.text = value; // the encoder derives the smallest scalar-aligned replace from the two strings

text.text = txt`${value.slice(0, 8)}${ok`${value.slice(8)}`}`; // a styled document is restated as a document
```

{/*
write
- Question: what do I do on a keystroke?
- Paragraph 1: assign. The planner diffs the previous text against the new one by common prefix and suffix, aligned
  to Unicode scalars, and sends the engine that one replace; a keystroke is an insert of one character, not a
  re-shape of the paragraph. `set({ text })` is the same call.
- Paragraph 2: a styled document is restated as a document, never as offsets; assigning a plain string clears the
  runs, assigning a `txt` document replaces them. There is no `insertText`, `setSpan`, or offset helper: any such
  call would let a caller hand the engine an offset the tree cannot express.
- Close by pointing at Interaction for the caret and selection side of the loop.
- Shape: two paragraphs, one pointer.

notes · internals
- the minimal edit: common prefix and suffix by code point, `{ start, deleteCount, insert }` —
  `engine-encoding.ts#minimalTextMutation` (`:312–335`), applied per dirty paragraph at `internal/render-planner.ts:855–859`
- assignment is `set({ text })` — `three/text.ts:676–678`; a plain-string update resets spans to `[]` —
  `engine-encoding.ts#replacedContent` (`:297–303`), called at `three/text.ts:721`
- unchanged spans identity is preserved across an update — `three/text.ts:1451–1456`
- a measurement query re-sends the whole text rather than a diff — `internal/render-planner.ts:812–819`
- the removed helpers `insertText`/`deleteText`/`replaceText`/`setSpan`/`removeSpan`: none exist in `three/text.ts`
  and no decision in `.agents/docs/planning/decision-register.md` names them (grep at codex `1dc580a87`); name them in prose
  only as "there is no offset helper", not as something that was removed
- the scene — `site/examples/src/scenes/editing/scene.tsx`: a typist restates the line as nested runs every
  keystroke (`config.ts#runsOf`), so the document is always the tree; the counter reads `commitState()` back. The twin
  `three.ts` assigns `text.text = value` for a keystroke and a `txt` document for the styled line
- observed: the counter reads `committed` at revision = keystrokes + 1 (the initial state is revision 1), so one
  keystroke is one revision; `pending` shows for the one frame between a keystroke and the root's next accepted
  shape
*/}
