## One application, one canvas

## Two scenes

```ts
import { glyph } from '@pmndrs/glyph';
import { ThreeConfig } from '@pmndrs/glyph/three';
import { Scene } from 'three/webgpu';

const app = glyph.handle('app', ThreeConfig);
const hudScene = new Scene();
scene.add(app.createText({ font: Inter, text: 'world' }));
hudScene.add(app('hud').createText({ font: Inter, text: 'HP 100' })); // same handle, second root
```

```tsx
import { GlyphProvider, Text } from '@pmndrs/glyph/react';

export function Hud() {
  return (
    <GlyphProvider handle={handle('hud')}>
      <Text font={inter}>HP 100</Text>

```

{/*
write
- Question: I have a HUD scene; do I need another handle?
- Paragraph 1: no. A root discovers its scene from its attached texts and refuses to span two; a second scene is a
  second named root on the same handle. Roots are terminal — `app('hud')('deeper')` is a type error — and names are

- Paragraph 2: in R3F a portal into another scene gets a `GlyphProvider` with the named root, so texts under it bind

## Two handles

```ts
import { glyph } from '@pmndrs/glyph';
import { ThreeConfig, defineThreeConfig } from '@pmndrs/glyph/three';

const labels = glyph.handle('labels', ThreeConfig);
const hud = glyph.handle('hud', defineThreeConfig({ transformMode: 'direct', compositing: 'independent' }));
labels.createText({ font: Inter, text: 'shared face' }); // both bind Inter without loading it twice
hud.createText({ font: Inter, text: 'HP 100' });
hud.dispose(); // its roots and texts; Inter and the labels handle are untouched
```

{/*
write
- Question: when is a second handle right?
- Paragraph 1: a handle per adapter configuration — transform mode, allocation mode, default format, root material —
  or per teardown boundary you want to dispose as one. Both bind the same FontFace; the font library is process-wide
  and a handle only keeps a per-handle store of which selections it has bound.
- Paragraph 2: `defineThreeConfig` returns a pure descriptor; two handles from one config share no mutable state.
  Names are unique while live and reusable after `dispose()`.
- Shape: two paragraphs.

notes · internals
- options — `three/handle.ts#ThreeConfigOptions` (`:93–99`); defaults `'indexed'`, `'ordered'`, `'msdf'` (`:175–177`);
  "every handle still owns independent mutable state" (`:170`); spreading preserves hooks (`:264`)
- the per-handle FontFace store over the shared library — `glyph.ts:71–72`, `:107–116`; `font-face.ts#FontFaceHandleStore` (`:314`)
- unique live names, reusable after disposal — `glyph.ts:68`, `:76–79`; `docs/packages/glyph.md:127–128`
- `CodecTransformMode = 'direct' | 'indexed'`, `CodecAllocationMode = 'ordered' | 'stable'` — `config/codec.ts:548–549`

## Workers and OffscreenCanvas

```ts
// main thread: copy the loaded face's bytes and hand them over
const worker = new Worker(new URL('./text.worker.ts', import.meta.url), { type: 'module' });
const [serialized, transfer] = await Inter.clone(); // fresh buffers; Inter stays valid here
worker.postMessage(serialized, transfer);
```

```ts
// text.worker.ts: its own engine, its own handle, the same font without a fetch
import { glyph, type SerializedFontFace } from '@pmndrs/glyph';
import { ThreeConfig } from '@pmndrs/glyph/three';
import { msdf } from '@pmndrs/glyph/raster/msdf';

self.onmessage = async ({ data }: MessageEvent<SerializedFontFace>) => {
  await glyph.init();
  const app = glyph.handle('worker', ThreeConfig);
  const Inter = glyph.fontFace(data, { format: msdf });
  await Inter.load();
  app.createText({ font: Inter, text: 'shaped over here' });
};
```

{/*
write
- Question: can shaping live in a worker, and how does the font get there?
- Paragraph 1: the ordinary path is the whole stack in the worker: engine, handle, renderer, and a transferred
  `OffscreenCanvas`. A worker has its own engine and its own Wasm copy; engine registrations, handles, and borrowed
  views never cross realms. Messages carry authored text state, not plan bytes.
- Paragraph 2: the font crosses by an explicit data clone. `await Inter.clone()` loads what is needed, copies the
  main GLB and every carried format into fresh buffers, and returns `[serialized, transfer]`; posting that pair may
  detach the copies without touching the source. `glyph.fontFace(serialized)` on the other side recognises the
  envelope and seeds its own cache, so the load there fetches nothing. Nothing does this for you.
- Paragraph 3: say what is gone. The earlier "shape in a worker, render on the main thread by transferring plan
  bytes" topology was removed with the async plan target; a cross-realm renderer would need a new, proven contract.
- Shape: three paragraphs.

notes · internals
- `clone()` on a face or a member — `font-face.ts:81`, `:217–219`, `:240–242`; the copy — `#cloneFontFace` (`:415–436`);
  `FontFaceTransfer = readonly [SerializedFontFace, Transferable[]]` — `font-face-transfer.ts:40`; D-313
- `glyph.fontFace(serialized)` — `FontFaceSource` includes `SerializedFontFace` (`font-face.ts:27`); proof with a Node
  Worker — `tests/integration/font-face-preinit.test.mjs:29–45`, `tests/support/font-face-transfer-worker.mjs:13–24`
- one engine per realm; registrations do not cross — `docs/planning/font-runtime-ownership.md:1151–1155`, `:1203`
- owned/transferred publication path removed — D-318, D-319 (`PlanTransport` "exposes no owned-publication copy")
- [verify] the worker example's `OffscreenCanvas` handoff to `WebGPURenderer` is three's, not Glyph's; link three's
  docs rather than restating it
*/}

## Device loss

{/*
write
- Question: what do I do when the GPU device is lost?
- Paragraph 1: three's renderer owns the device; Glyph's plan target does not, and rebuilds nothing on its own. The
  root's retained plan, revisions, and fonts survive; physical buffers, textures, and materials do not. A host that
  recovers its renderer then needs the root to republish a checkpoint rather than patches, from the last accepted
  revision.
- Paragraph 2: at HEAD there is no public "device lost" call on a Three root; the practical recovery is to dispose the
  affected handle and create a new named handle over the same FontFace — nothing is fetched or shaped anew as
  content, only re-bound. Write this as the recipe and flag the missing hook.
- Shape: two paragraphs.

notes · internals
- "Three's plan target does not own the GPU device; a device-owning renderer explicitly requests the same checkpoint
  only after rebuilding its lost-device resource pool" — D-285
- the checkpoint request lives on the planner control — `internal/render-planner.ts#PlanTargetControl.requestCheckpoint`

## Cardinality

| Relationship | Cardinality | Rule |
| --- | --- | --- |
| `FontFace` → handle | many-to-many | one shared resource graph; each binding a counted lease |
| handle → root | one anonymous + many named | roots cannot nest; a named root is terminal |
| root → `Scene` | at most one | two scenes, two roots |
| root → encoder | one | the root is the publication boundary and the acceptance frontier |
| engine → JavaScript realm | one | Wasm memory and borrowed views do not cross realms |
| renderer → device | the host's | Glyph holds leases on payloads, never on GPU objects |
