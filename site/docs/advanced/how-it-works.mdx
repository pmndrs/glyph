## Analysis

```ts
import { span, txt } from '@pmndrs/glyph';

text.set({ text: txt`Hello ${span({ color: '#ffd166' })`world`}` }); // validated here, analysed in Rust
```

{/*
write

- Paragraph 1: every property is validated where it enters — construction, `set()`, a hook — with the offending
  value in the error; style, layout, and constraints property lists are merged left to right and checked; spans are

- Paragraph 2: what JavaScript does not do. Scripts, bidi levels, line-break opportunities, and grapheme clusters

## Shaping

<glyph-proxy fit="cover" root="scenes" data-scene="shaping" aria-label="Eight scripts arriving one grapheme cluster at a time" aspect="16 / 9" />

{/*
write
- Question: how does a run become glyphs, and what happens when a font lacks one?
- Paragraph 1: each run is shaped with HarfRust against the stack's first font. Clusters whose glyph came back as 0
  are collected and re-shaped with the next font in the stack, once per stack depth; a cluster still missing after
  the last font stays glyph 0 in the last font tried. The re-shaped clusters are restored to logical order, so
  fallback never changes the reading order.
- Paragraph 2: fallback is decided by the shaper's `cmap` result, not by what the raster baked. A glyph the font maps
  but the raster did not include is a `RasterCoverageError`, not a fallback.
- Point at the proxy: the same shaper, eight scripts, only `language` and the face change.
- Shape: two paragraphs.

notes · internals
- HarfRust — `rust/shaper/src/lib.rs:19`; glyph flags — `engine/shaping_state.rs:643–653`
- fallback: every run starts on the stack's first font — `engine/state.rs:2781–2797`; one pass per stack depth
  (`:2799`); a `missing` cluster (`glyph_id == 0`, `:4120`) re-shapes with the next font — `:2856–2905`; test

## Layout

{/*
write
- Question: why is layout exact, and what does "exact" mean here?
- Paragraph 1: advances, cursors, slot boundaries, and extents are integers in fixed point, converted once per
  cluster under one rounding contract (round half up, `floor(value × 2^bits + ½)`), so native and Wasm builds agree
  bit for bit and integer sums are associative — which is what lets chunked SIMD summaries equal the scalar result
  exactly. Justification distributes in the same units. `f32` appears once, at the emission boundary.
- Paragraph 2: what is retained per paragraph: shaped runs, clusters in adjacency order, the line plan, positions.
  A font-size change re-scales advances without reshaping; a width change re-runs only fitting and positioning;
  `measure()` and `glyphs()` read the retained result through separate synchronous calls and never wait for a
  publication.
- Say "sixteen fractional bits" only after the register catches up (see the in-flight note); until then say
  "integer layout units under one rounding contract".
- Shape: two paragraphs.

notes · internals
- the unit and contract — `rust/shaper/src/engine/layout_units.rs:1–34` (`LAYOUT_UNIT_BITS = 16`, 1/65,536 of a

## The render plan

| Table | Holds |
| --- | --- |
| resources | acquire, update, retain, by id and generation |
| buffers | ensure a physical buffer: program, scalar type, vector width, capacity |
| patches | coalesced dirty byte ranges into those buffers |
| primitives | one record per glyph, decoration, inline object, or clip |
| draws | ordered spans: program, resource, material, transform, clip, depth key |
| retirements | resources and buffers released after a publication generation |
| diagnostics | engine-reported, not consumed by three |

{/*
write
- Question: what does Rust hand back?
- Paragraph 1: the planner walks glyphs in logical order, packs them into storage batches keyed by technique,
  program, and resource, and cuts a draw wherever the program's key mask says something changed. The output is one
  publication: a 144-byte header (engine revision, plan revision, publication generation, required base revision,
  flags, status, counts and offsets) followed by seven tables, written into one of two slots in Wasm memory.
- Paragraph 2: a renderer never reads those tables. The engine projects them into a typed `CommandBufferView`
  — resources, buffers, patches, retirements, and a display list of batches and root instances whose references are
  already resolved bindings — and lends it for the length of one synchronous `decode`. Point at Render plan for the
  fields.
- Shape: two paragraphs.

notes · internals
- header layout and size — `generated/text-shaper-abi.ts` `layouts.engineResult` (`:589–627`, `"size": 144`);
  table offsets/counts — `internal/plan-view.ts:13–46`; the table names — `internal/render-planner.ts#RenderPlanTableName` (`:76–84`)
- output cap 64 MiB — `internal/frame-wire.ts:19` (`MAX_TEXT_ENGINE_OUTPUT_BYTES`); Three's limits —
  `three/handle.ts:222–236` (4,096 paragraphs, 65,536 clusters/lines/regions, 64 KiB request, 256 KiB result)
- projection — `config/glyph.ts#TypedUpdatePhases` (`:137–142`), `#BorrowedTypedCommandBuffer` (`:148–157`); D-309, D-314
- draw cut rule — `rust/shaper/src/engine/stable_plan.rs#compile_ordered_draws` (`:1386–1479`); see Performance
*/}

## The retained frame transaction

![The retained frame transaction: the app assigns desired state, shape publishes each dirty root once, the planner lends a borrowed plan, the renderer decodes, resolves and prepares, then commits or discards.](/examples/diagrams/frame-transaction.svg)

```ts
import { glyph } from '@pmndrs/glyph';

text.set({ text: 'changed' }); // desired state; the root is now dirty
glyph.shape(); // stage every dirty root → one Wasm call → decode → commit or discard → settle
renderer.render(scene, camera); // three submits the meshes; a clean frame never re-enters Wasm
```

{/*
write
- Question: what is a frame, transactionally?
- Paragraph 1: `glyph.shape()` is synchronous, non-reentrant, and a no-op when nothing is dirty. It stages every
  dirty root — a root's `prepare` may decline (fixed capacity) — writes one batch entry per root, and makes one
  Wasm call for all of them across every handle. Rust processes the entries in order and reports status per entry,
  so one root can fail without another's renderer state being touched.
- Paragraph 2: per root, back in JavaScript: adopt the result, open one engine-wide borrowed scope, `decode` the
  projected view into staged host objects, `commit` or `discard`, close the borrow, then settle: accepted roots mark
  their texts committed and refresh their measurements; a rejected root keeps its last accepted draw and retains the
  error on its texts. `shape()` rethrows after every root has been visited — one error, or an `AggregateError`.
- Paragraph 3: revisions. Each request states the engine revision it expects, the plan revision it consumed, and
  the publication generation it last acknowledged. A publication is a checkpoint that replaces everything when the
  consumed revision is not current, and a set of patches otherwise. A rejected accept leaves every revision where
  it was, and an unchanged frame is never retried.
- Shape: three paragraphs.

notes · internals
- `_shape` — `glyph-engine.ts:387–433`: reentrancy guard (`:389`), empty fast path (`:390`), stage (`#stageShapeParticipants`,
  `:435–459`), batch (`#updateShapeBatch`, `:461–528`: descriptor per root `:479–486`, the call `:490`, adopt `:499–507`,
  borrowed scope `:508–520`, settle `:521–527`), rethrow (`#settleShapeParticipants`, `:530–555`)
- the staged planner contract — `internal/render-planner.ts#StagedRenderPlanner` (`:355–362`); D-312, D-318, D-319
- the root hooks — `three/handle.ts:249–254` (`prepare`, `accepted`, `rejected`); `three/text.ts#ThreeRoot.prepareShape`
  (`:436–449`), `.acceptShape` (`:451–460`), `.rejectShape` (`:462–465`)
- `decode` returns `{ commit, discard }` — `config/glyph.ts#GlyphRenderer` (`:506–510`), `#PreparedRendererCommit` (`:495–499`)
- revisions — `rust/shaper/src/engine/frame.rs#UpdateRequest` (`:106–119`: `expected_engine_revision`,
  `consumed_plan_revision`, `acknowledged_publication_generation`), `#PreparedUpdate` (`:157–163`: `checkpoint`,
  `required_base_revision`); A/B slots — `engine/transport.rs:175`, `:252–275`, `:342`
- renderer failure keeps the last accepted plan revision, generation, and error; no retry of unchanged frames — D-285
*/}

## What three.js does with it

| Path | Enters Wasm | Cost |
| --- | --- | --- |
| text, style, layout, font, or material changed | once per `shape()`, for every dirty root together | shape, layout, plan, decode, commit |
| position, rotation, scale, visibility changed | no | matrix uploads for the rows that changed |
| nothing changed | no | nothing |

{/*
write
- Question: what is a draw, concretely, and why does moving a text cost only a matrix?
- Paragraph 1: three's config hands the root's executor back as the renderer. On a `replace` display list it
  realises one `THREE.Mesh` per draw span under the root's draw object — the codec's buffers as storage attributes,
  one material per span from the format's factory — and reuses meshes whose realization key (program, resource,
  material, buffers, clip, depth key, transform generation, geometry) is unchanged; on an `unchanged` display list it
  applies patches into the same buffers. `renderOrder` is the span's index; `userData.pmndrsGlyphRunStart` is its
  first record.
- Paragraph 2: every frame after, three's own `updateMatrixWorld` reaches the root's draw object, which runs
  `shape()` (a no-op when clean) and then syncs matrices: for each text whose world matrix changed, one 16-float row
  goes into the transform storage attribute as an update range; an invisible text gets a zero matrix. A text that
  only moved never reaches the planner.
- Shape: two paragraphs; the table is the summary.

notes · internals
- the renderer is the root's executor — `three/handle.ts:215–220`, `:238–260`; `three/engine-plan-target.ts#ThreeTextRenderPlanExecutor`
- `replace` vs `unchanged` — `three/engine-plan-target.ts#prepareBound` (`:291–369`); commit — `#commit` (`:371–423`)
- one mesh per span, reuse by key, `renderOrder = base + drawIndex`, `userData.pmndrsGlyphRunStart` —
  `three/internal/draw-realizer.ts:141–187`
- traversal → `shape()` → transform sync — `three/text.ts:139–142`, `:478–493`; the sync —
  `three/transform-synchronizer.ts:20–88`
- the draw root is named `@pmndrs/glyph:anonymous` or `@pmndrs/glyph:<name>` — `three/text.ts:197`
*/}
