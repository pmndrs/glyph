## Where time goes

![Two paths through a frame: a semantic change goes through one Wasm batch and a decode-and-commit; a transform-only change syncs matrices without entering Wasm.](/examples/diagrams/frame-paths.svg)

| Path | Enters Wasm | What it costs |
| --- | --- | --- |
| `text`, `style`, `layout`, `constraints`, `font`, or `material` changed | once per `glyph.shape()`, every dirty root in one batch | shape, layout, plan, decode, commit |
| position, rotation, scale, visibility, reparenting changed | no | one 16-float row per changed transform, uploaded as a range |
| `measure()` on unchanged text | no | a cache read |
| nothing changed | no | `shape()` returns at its first check |

| Measured, 25,515 positioned glyphs, one paragraph | Median | p95 |
| --- | ---: | ---: |
| cold (first shape) | 17.84 ms | 18.99 ms |
| font size changed | 6.32 ms | 6.64 ms |
| column width changed | 3.04 ms | 4.60 ms |
| text replaced | 13.84 ms | 14.01 ms |

{/*
write
- Question: which door did my frame go through?
- Paragraph 1: the cheap door. Every frame, three's own `updateMatrixWorld` reaches the root's draw object, which
  runs `glyph.shape()` (a no-op when nothing is dirty) and then a transform sync: for each text whose world matrix
  changed, one 16-float row is written into the transform storage attribute and marked as an update range. No Wasm,
  no allocation; camera motion costs nothing at all because only the texts' matrices are read.
- Paragraph 2: the expensive door. A semantic change marks its root dirty; the next `shape()` stages every dirty root

## Draw boundaries

| Boundary | Why it splits |
| --- | --- |
| program (raster format) | a different pipeline and shader |
| resource (font atlas or page) | a different bound texture |
| material | a different node graph, when the program keys on material |
| transform | only in `transformMode: 'direct'`, where each draw carries its own matrix |
| clip | a different scissor |
| paint layer under `ordered` | a run cannot cross an incompatible run without changing what draws over what |

```ts
import { glyph } from '@pmndrs/glyph';
import { defineThreeConfig } from '@pmndrs/glyph/three';

three.setCompositing('independent'); // this root, from its next shape()
const hud = glyph.handle('hud', defineThreeConfig({ compositing: 'independent' })); // or per handle
```

- Question: why do sixty labels cost sixty draws, and what folds them?

## Roots

```ts
import { glyph } from '@pmndrs/glyph';
import { ThreeConfig } from '@pmndrs/glyph/three';

const app = glyph.handle('app', ThreeConfig); // the anonymous root: text that changes together
const ticker = app('ticker'); // a named sibling: text that changes every frame
ticker.createText({ font: Inter, text: '00:00' });

app.gpuBytes; // retained buffers, transform table, and atlas bytes for this root
ticker.gpuBytes;
text.gpuBytes; // the root's figure, seen from a member
```

{/*
write
- Question: when is a second root worth having?
- Paragraph 1: a root is one publication stream: one planner, one command buffer, one acceptance. Everything on it
  republishes together, so a ticker that changes every frame on the same root as a page of static copy makes the
  static copy part of every batch entry's reconcile. Put text that changes at different rates, or that lives in
  different scenes, on different roots; `handle(name)` gives a sibling that shares fonts and the engine and nothing
  else.
- Paragraph 2: `gpuBytes` is the honest number: buffers, the transform table, and the atlas or page bytes this root
  retains. A text reports its root's figure, not its own share.
- Avoid: calling a root a "batch"; that word belongs to the plan.
- Shape: two paragraphs.

notes · internals
- `handle(name)` returns one idempotent terminal sibling root — `config/glyph.ts#GlyphHandle` (`:581–589`),
  `#GlyphNamedRoot` (`:575–578`); D-307
- unchanged roots do not enter the batch — `glyph-engine.ts#stageShapeParticipants` (`:435–459`, a root that
  declines returns `undefined` and is `SKIPPED`); a root's `prepare` — `three/text.ts#ThreeRoot.prepareShape` (`:436–449`)
- `gpuBytes` sums retained buffers, the transform attribute, bitmap textures, MSDF atlases, and Slug pages —
  `three/engine-plan-target.ts#ThreeTextRenderPlanExecutor.gpuBytes` (`:126–140`); root getter `three/text.ts:214–216`;
  text getter `:661–663`
- fonts are shared by every handle through one library — `glyph.ts:107–116`
*/}

## Capacity

```ts
import { glyph } from '@pmndrs/glyph';
import { defineThreeConfig } from '@pmndrs/glyph/three';

const labels = glyph.handle('labels', defineThreeConfig({ capacity: { size: 512, policy: 'fixed' } }));
labels.setCapacity({ size: 1024, policy: 'chunk' }); // later; only republishes if something was over budget
```

| Policy | Allocation | Over budget |
| --- | --- | --- |
| `grow` | resize to what the content needs | never |
| `chunk` (default, `size: 4096`) | resize in multiples of `size` | never |
| `fixed` | never past `size` | the root declines the batch and keeps its last accepted draw; `commitState()` stays `pending` |

{/*
write
- Question: what does capacity buy, and what does `fixed` cost me?
- Paragraph 1: capacity is glyph-instance slots per physical buffer, sized before shaping from UTF-16 length, which
  is a safe upper bound on glyphs. `grow` and `chunk` differ only in how often the buffers are reallocated; `chunk`
  amortises.
- Paragraph 2: `fixed` is a promise to the GPU, not a limit on the text. When desired text exceeds it the root does
  not publish, the last draw stays, `measure()` still answers, and the decision is retried on every traversal — so
  shortening the text or raising the cap recovers without any other change.
- Shape: two paragraphs; the table carries the policies.

notes · internals
- policies and the UTF-16 bound — `text-properties.ts#GlyphBufferCapacity` (`:7–16`), `#normalizeGlyphBufferCapacity` (`:19–31`)
- root default `{ size: 4_096, policy: 'chunk' }` — `three/text.ts:191–194`
- `fixed`: `required = Σ text.length`; over budget returns `false` from `prepareShape` and records `capacityExceeded` —
  `three/text.ts:1260–1270`; `setCapacity` invalidates only when exceeded — `:1115–1119`; root setter `:240–247`
- `commitState()` → `'pending'` while uncommitted — `three/text.ts:756–764`; D-282 (fixed keeps the last accepted
  draw and retries every traversal), D-131 (size + policy are the only public capacity dimensions)
*/}

## Raster density and DPR

```tsx
import { Text } from '@pmndrs/glyph/react';
import { Canvas } from '@react-three/fiber/webgpu';

export function Hud() {
  return (
    <Canvas dpr={[1, 1.5]}>
      <Text font={inter} rasterPixelRatio={2}>
        raster at 2×, whatever the canvas does
      </Text>
    </Canvas>
  );
}
```

```ts
text.rasterPixelRatio = 2; // a Text property; layout does not change
```

{/*
write
- Question: which pixel ratio is mine?
- Paragraph 1: the canvas DPR is the host's: it sizes every render target, and with a post chain it multiplies float
  targets. The landing clamps to `[1, 1.5]` because its post chain at native DPR was measured at 732 MB of texture.
- Paragraph 2: `rasterPixelRatio` is a Text property and only chooses raster density: for Bitmap it selects the
  strike (`fontSize × rasterPixelRatio` in ppem, nearest wins); for MSDF and Slug it scales nothing on the GPU. It
  does not touch layout. Use it when text is seen larger than authored (magnified, close to the camera), and
  cross-link the steep-angle scene on Text in 3D, which is the same trade seen from the format side.
- Shape: two paragraphs.

notes · internals
- `rasterPixelRatio` positive and finite, default 1 — `internal/render-planner.ts:1585–1588`, `:1627`; Text
  getter/setter `three/text.ts:699–703`; React prop `react.ts:91`
- strike choice `targetPpem = cssFontSize × rasterPixelRatio` — `internal/bitmap-strike.ts:11`
- the landing's clamp and the 732 MB measurement — this repo, `site/landing/src/main.tsx:46–52`
- [verify] "clamping to 1.5 cut it to 243 MB": the number is in no source; re-measure before stating
- [verify] whether MSDF or Slug read `rasterPixelRatio` anywhere: grep the Rust gather (`plan_input.rs`) before
  claiming "scales nothing"
*/}

## Pixel snapping

```ts
three.createText({ font: Inter.bitmap, text: 'HP 100', style: { fontSize: 16 }, pixelSnapping: true });
three.createTextGroup({ pixelSnapping: true }); // inherited by members that do not state their own
```

{/*
write
- Question: when should a text snap?
- Two sentences: `pixelSnapping` rounds a Bitmap quad to whole device pixels, so a HUD at rest is texel-exact and a
  moving one shimmers; MSDF and Slug reconstruct their edge from screen-space derivatives and never snap, so the
  flag is accepted and ignored for them. It is part of the material key, so snapped and unsnapped texts of one font
  are two draws.
- Shape: one short paragraph.

notes · internals
- Text and TextGroup carry the flag — `three/text.ts:612`, `:641`, `:971`; it enters the material realization key —
  `three/internal/material-realizer.ts:154`, `:170`
- Bitmap's vertex path rounds the physical position — `tsl/bitmap-shader.ts:78`, `:104`; Slug publishes no
  `clipPosition` and "must keep the default projection" — `tsl/slug-shader.ts:83–84`
- [verify] that MSDF ignores the flag at the shader level (read `tsl/msdf-shader.ts` for a `clipPosition` output)
*/}
