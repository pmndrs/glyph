# Independent old/new architecture and hybrid decision — 20 October 2026

**Decision.** Keep E2 (`a829` package source, archived `28fd0413…`, shipping shaper `01001ff6…`) live and the correct E3 hybrid preserved but inactive. The best next product direction is a **shared semantic-to-physical preparation representation with a coarse dense publication mode**, not another ordered-rope micro-cut. It is a conditional architecture, not yet an authorized code wave: the present source and exact Bitmap replay do not identify a complete repeated producer/consumer transform that it can delete without moving comparable work into every synchronous setter. Run one bounded, paired phase/ownership discriminator described below; then either implement the specified deletion or stop this line. The seven-family parity goal remains open. No timing, build, installation, source, or Git mutation was done for this review.

## Where the old and new systems win

The old main path (`origin/main` locally resolves to the reported `4e25a96a…`; main source is an observed Git object, while published 0.1.0 is authenticated as a separate archive rather than assumed source-identical) lets `RenderPlanner._updateText` validate/resolve a new authored state and mark it dirty. At one later `#compileFrame`, it collects all dirty paragraphs, derives text mutations, encodes one frame, and asks Rust to prepare, position, gather, and publish. An intervening query can prepare on demand. For 1,024 setters with no reads and one scene publication, this amortizes Rust crossing, frame preflight, root setup, and publication over the batch. A superseded intermediate setter can cost much less. Main's measurement-only speculative path can omit positioning until publication. See `git show origin/main:packages/glyph/src/internal/render-planner.ts` around 631–694, 881–910, 1086–1145 and old `state.rs::measure_paragraph_inner`/`prepare_update_inner`.

HELD's `RenderPlanner._updateText` calls `#prepareTextCandidate` before adopting each changed state. That builds a single-paragraph request and calls `PlanTransport.prepareParagraph`; `TextEngine::measure_paragraph_inner` runs the same Rust paragraph executor, positions a changed paragraph, and commits a queryable semantic revision. `#compileFrame` later carries lifecycle/order and accumulated renderer dirt, with empty text/style/geometry sections, into one publication. A subsequent measure, glyph inspection, independent split, or copy reads that prepared state. Accepted semantic revision and renderer generation remain distinct, including abort/rejection behavior. See current `render-planner.ts` around 698–835, 1234–1321, 1323–1370; `state.rs` around 1376–1577 and 1578–1980; [retained prepare/publish decision](../../../.agents/docs/planning/decisions/retained-prepare-publish.md). This changes where work occurs: a setter must do real semantic work and one crossing; a later publication must not shape again. It buys immediacy and reuse for reads but cannot gain old main's deferred-setter advantage on a no-read bulk operation without changing the accepted contract.

Within HELD, the sparse path also has real advantages. Paragraph state retains text identity and aligned Unicode/shaping/flow/positioning structures; 32-record copy-on-write rope leaves preserve clean ranges. Same-length replacement uses a packed UTF-16 comparison to find edit islands, then the existing Unicode/HarfRust/flow guards decide whether each island is safe; queued owner IDs and ordered intervals bound publication. Inspection materializes requested columns from the prepared revision, and independent copy no longer relies on an uncommitted renderer frame. This explains the E2 same-machine sparse borrow after one edit (0.212 ms p50 versus main 0.269 and release 0.267), per-glyph inspection after width change (4.756 versus 7.510/9.307), and independent edit/copy (2.089 versus 2.996/6.069), though the exact comparisons have their recorded exclusions. Rope sharing is a source-level mechanism; those timings establish whole-operation results, not its isolated causal contribution.

The tug of war has two separate axes. First, old main batches semantic preparation at a late boundary; HELD pays 1,024 Rust setter transactions and their preflight/shape/flow/position tails to make each revision immediately queryable. A read after every setter reverses the old advantage because main must prepare on demand repeatedly or materialize more data later. Second, sparse structural sharing favors ropes/correspondence; dense changes still gather SoA columns, admit ordered instances, encode packed physical bytes, compare old buffers and publish patches. A dense path that walks old leaves less may add scratch, fallback, or field work. A layout that makes renderer columns at the setter may only move the gather cost upstream, and can duplicate semantic/renderer state or lose dense SIMD locality. This is why “make a fast path” is insufficient; the producer, shared representation, consumer, and retired owner must be named together.

E2's one frozen candidate was reused against same-machine main and published 0.1.0 in the complete matrix. Dense 512 p50/p95 was 10.143/11.443 ms versus main 7.910/8.936 and release 8.582/9.430. Dense 1,024 was 19.762/22.341 versus 16.844/18.395 and 17.100/18.684. This is a material dense gap, while sparse/read rows above win. The eight-block, 145-identity matrix has excluded clock/mode rows; a neutral classification is not parity. [E2 report](../held-codec-scratch-local-2026-10-20/README.md) owns samples and provenance. Do not compare these absolute times with E3's separate matrix as if they were paired blocks.

One exact E2 current-1,024 sampled CPU capture assigned 835,835 µs/560 samples to setter preparation ancestry, 358,876 µs/240 to publication, and 99,122 µs/42 unattributed over 80 iterations. It omitted a Labs returned-text-count DFS and is not an elapsed or removable-time partition. It nevertheless makes a publication-only rescue an unsupported bet: even abolishing a substantial publication coefficient would leave the many setter transactions. There is no equally authenticated old-main _phase_ capture, so it does not quantify the incremental semantic cost versus old. [Profile receipt](../held-codec-scratch-local-2026-10-20/current1024-profile-authentication.json).

The new actual Bitmap native replay is particularly useful because it captures the shipping `28fd` request/input/output stream and matches every one of 4,099 native result slices (1,977,392 bytes) over 6,157 ordered events, with phase cardinalities 2,048 initial preparations, then 1,024 preparation calls and one publication in each forward/reverse edit. The immutable manifest/events and shipping identities are in `bitmap-native-work-ledger-01/identity.json`; all output comparison and source pre/post hashes are in `prepost-and-consistency.json`. The diagnostic hooks are Rust `cfg(test)`; shipping Wasm remains a separate witness. Native Codec execution is scalar, so the four-row groups are **eligibility**, not observed Wasm SIMD instructions or speed. The replay bypasses `UpdateBatchTransport::process`, allocation/descriptor work, JS private buffers, GC, and host/GPU behavior. It is neither a timing run nor a seven-family oracle.

For each edited 1,024-label phase the replay shows 1,024 HarfRust calls for 10,240 UTF-16 units, 1,024 full cluster builds and 10,240 positioned rows. The apparent 10,240 `shapeScratchMovedGlyphs` accompany 1,024 `core::mem::swap` arena ownership transfers in `state.rs` around 5115–5148; they are **not** 10,240 copied glyph rows. Positioning produced 5,120 new identities and 5,120 corresponding prior identities, all with nonzero accumulated masks; half are full masks. Publication visits 10,240 source rows, selects 9,216, has 1,024 recordless rows, and executes a single 9,216-record Codec run (2,304 four-row eligible groups). It compares 589,824 physical bytes, suppresses 221,184 equal bytes, and emits 368,640 plan write bytes plus separate session writes. Six of nine plan buffers are written. The output byte identities and write-byte consistency support these counts; they do not assign latency to either stage. [Ledger](bitmap-native-work/native-work-ledger-01.json.raw), `codec_gather.rs::update_retained_source`, `ordered_plan.rs::write_changed_ranges`, and `plan_packing.rs::execute_run` are the anchors.

The first ledger (`bitmap-native-work-ledger-01`) had two observer coverage gaps: per-lane gather reads omitted `update_retained_position_only`, and it did not report an accepted positioned-arena source total. A second independently reviewed replay (`bitmap-native-work-ledger-02/native-work-ledger.json`, SHA-256 `1bdfa7e60a850a14b20fc06685a709d0eb2f669150ac11bd69eff432a24fea1b`) adds 12,288 position-only f32 reads per edit publication (109,568 total versus the first ledger's 97,280), leaves 97,280 f32 writes and 48,128 changed slots unchanged, and records 10,240 prepared positioned source rows with availability one at each publication. It reports the same 6,157 events and exact 4,099-result pass. The independent [correction review](fresh-work-ledger-correction-review.md) closed all three observer findings for this pinned trace; these counts are accepted only as bounded native scalar work evidence, not performance or shipping-Wasm acceptance. `positioning.rows` still counts setter assignments, hence zero during publication does not mean zero prepared rows. `gather_output_source_rows` is read after gather, not an independent accepted-state count; retained source match/mismatch counts are source-slot comparisons, not physical identity proof. Neither ledger measures elapsed time.

The physical writer already chooses active buffers by dependency mask for each changed range, copies valid prior slices, emits only changed bytes, and preserves one straight 9,216-record Codec run. The mixed full/narrow masks make the complete changed range's union broad; splitting into many mask-homogeneous runs could shrink some physical work while increasing branching, small-run overhead, allocation, and loss of SIMD grouping. The 221,184 equal-suppressed bytes are avoidable _candidate computation_ only if an earlier authenticated semantic-to-physical proof can show equality without doing equivalent work; a post-Codec byte compare cannot recover its cost. The 368,640 emitted plan bytes and session writes are real output for this fixture. Calling them removable would be false. The present plan's producer/consumer passes have separate duties: positioned semantic state, binding and recordless selection, packed Codec fields, ordered batch/slot admission, encoded physical bytes, renderer acceptance. No full redundant pass is established by source or ledger.

## Coherent hybrid to test, not assume

The target shape is **one semantic executor with two coarse consumption modes over the same prepared state**. Setter preparation keeps the current paragraph-owned text/Unicode/HarfRust/flow/positioned SoA and its exact dirty masks; queries and independent splits read that accepted revision. A sparse publication walks the proven owner/rope intervals and copies clean leaves. A dense publication scans those _same_ positioned columns sequentially and writes the existing packed output, without building retained source correspondence, changed-leaf vectors, or per-record source maps that a complete replacement cannot reuse. Both modes meet at the current `PlanInput`/Codec and ordered compiler, with one ABI, one physical storage representation, and one renderer acceptance transaction. The mode guard should be a coarse fact already known after owner admission (complete dirty frontier plus exact layout/key/selection preconditions), never a per-glyph density guess or a second Unicode model. The dense mode must retire the corresponding retained-gather/correspondence work for that publication, not append another pass. Existing `prepare_update_inner` already attempts this general idea; E3's reset is its tested incarnation, so renaming it or restoring it is **not** a new wave.

The genuine alternative at the preparation layer is to make paragraph-owned positioned columns also the publication's _borrowed source view_. Today `positioning.rs` owns accepted glyphs/semantic masks; `state.rs::append_planner_gather` and `codec_gather.rs` materialize a separate `GatherSource` rope, selected `PlanGlyph` records and flat f32/u32 lanes for the Codec. A shared view would have to carry stable ID, recordless selection, binding/program identity and per-field dependency evidence through the accepted paragraph revision, then let a dense compiler read those SoA slices without repacking fields and a sparse compiler retain/copy only changed slices. It could remove an actual gather construction and improve locality. It could also force renderer-specific selection work into every setter, duplicate live columns, lengthen abort/rollback lifetimes, and lose the 9,216-record wide run. No one should implement it from the current ledger alone. A viable prototype must replace at least one named `codec_gather.rs` owner (`sources`, `glyphs` or field columns) rather than cache a second copy; preserve fallible allocation and reset, multi-font/recordless behavior, independent split, and cold whole-output equivalence. The alternative is not a second executor or segmented physical ABI.

The expected work model clarifies the bet. For `N` independent changed labels of `u` units each, HELD must perform `N` synchronous accepted paragraph preparations and at least inspect the authored `Θ(Nu)` input; HarfRust/Unicode/flow costs depend on validated context and are not assigned a universal linear bound. Dense publication then touches `G` source rows and `P` selected physical records, plus `F` active field/byte lanes, so a fully changed output remains `Ω(PF)` for the relevant output bytes. Sparse publication can use `O(k log N + changed leaves/fields)` routing for `k` dirty owners, but worst-case context propagation remains broad. A shared positioned view could remove one `Θ(GF)` gather materialization and its live columns while keeping one `Θ(PF)` encoding/output pass; it cannot remove the `N` setter calls or emitted bytes. Its extra metadata should be `O(G)` only if it _replaces_ existing source/field metadata, and transient work should remain bounded by changed leaves plus final output. If it instead adds `O(GF)` retained columns or produces fields during each setter, it has failed the ownership objective before timing.

## One bounded discriminator and follow-on decision

The **observer-only** correction in ledger 02 is complete and independently reviewed for this trace: position-only gather reads, accepted positioned-row availability/total, exact 4,099-result replay, and immutable input/source hashes. Its corrected counts replace ledger 01 for bounded field-traffic decisions. No new capture or timing is needed. Treat total row/byte counts as work, not latency.

Then take **one paired, source-matched dense 1,024 phase experiment** using existing package workflow hooks: in main/release/E2 with the same authored inputs and result oracle, measure total setter/preparation, publication native, JS/host and unassigned time separately, while recording crossings, request/result bytes, allocations and exact output bytes. It must be an untimed diagnostic outside the acceptance matrix, or a fixed-size profiled capture whose overhead is disclosed, with matched artifacts and no favorable reruns. The purpose is to resolve three choices: (A) setter transaction/semantic work is the excess, (B) gather/physical compiler is the excess, or (C) both are material. E2-only sampled ancestry cannot decide this relative excess. Stop after this paired comparison; if matching old source/profile instrumentation would alter released bytes or cannot preserve the exact workload/output, record the failed feasibility and do not infer a phase delta from unmatched probes.

If **A** dominates, inspect the current `measure_paragraph_inner` transaction and `#prepareTextCandidate` request/return boundary for one complete repeated owner to delete while preserving immediate query state. The strongest candidate is a setter-produced _measurement/sidecar or repeated root-wide preflight_ that the no-read bulk fixture does not request and publication does not consume. Name its producer and all consumers first; if every step is required to commit the prepared revision, stop rather than defer work to publication. A candidate deletes the old sidecar/preflight path at that call and uses the existing accepted paragraph state for queries. It must retain complete UTF-16/HarfRust/flow/positioned cold equivalence after **each** setter, including arbitrary Unicode/font/width, not merely after the frame. It should preserve one request codec, exact failure/rollback and snapshot semantics, and bound new memory to reused transaction scratch. The arena-swap counter must not be offered as a copy-deletion target.

If **B** dominates and corrected lane counts show a substantial repeated gather/encode of fields whose physical outputs remain equal, prototype the shared positioned-column view above, with a direct dense consumer and existing sparse consumer. The deleted work must be named concretely before edit: e.g. replace a `gather_fields` field append and corresponding `update_fields` rewrite with borrowed positioned column slices for the same Codec input, or replace a full retained-source correspondence build with direct dense source enumeration. Keep a single validated Codec program and wide four-row grouping; if field-specific runs fragment it or require extra per-setter renderer work, reject. The old gather field storage/path is removed in the same wave, subject to a transitional experiment branch; an additional permanent cache fails this design.

If **C**, use one coherent bounded wave only when it deletes a measured owner on both sides. Otherwise keep E2 and report the contract-normalized difference rather than spend the allowed post-parity boost attempts. Any accepted wave gets independent cold per-setter layout/IDs/Unicode/flow and per-publication exact physical buffers/patch/order/bindings compared to a separate cold compiler, including new/recordless identities, mixed masks, late retained miss, allocation failure, abort, renderer rejection/retry, borrowed lease, and independent split. Then one frozen candidate archive is compared on the same machine with fresh main and published 0.1.0 across all seven families: long Unicode/shape/flow; dense 512/1,024; width/cold/inspection; authored ingress; sparse/root publication; selected copy; tails/memory/delivery. Preserve p50/p95, exclusions, API/ABI/peer/lifetime, optimized Wasm size, live/peak memory, browser pixels/uploads and output identity. Parity requires the dense operations to close against **both** controls without materially losing sparse/read wins; neutral or an aggregate win count is insufficient. Only after parity do the authorized up-to-three further coherent boost waves begin. If the discriminator finds no removable owner, stop this architecture line with E2 held and E3 preserved; no arbitrary 5% floor or impossibility claim follows.
