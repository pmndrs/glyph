**Status: final for the completed E3 three-arm matrix; E3 is not admitted as the live path.**

20 October 2026. Read-only review of frozen worktree `a829b86bfefcd0e39b6d947cb7a2571776cd06a0` plus the uncommitted hybrid in `state.rs` and `work_attribution.rs`. ## Decision

Keep the semantic contract and the sparse retained pipeline. **Do not admit frozen E3 `37c1e088…` as the live path.** It is correct in scoped output/ABI tests, but the completed direct same-machine comparison shows no dense win, material dense and sparse losses, and higher diagnostic allocation/size cost. Preserve the **whole correct E3 source variant** under a named ref or recoverable snapshot together with its exact archive, diff, tests and evidence before retiring its branch choice; then restore the prior `28fd0413…` live path through a reviewable source operation owned by root. Do not keep only E3 tests or discard its source. This rejects E3 for admission, not the general possibility of a hybrid. Any future density choice must still use one Rust semantic executor and one packed output representation, and must earn deletion of a complete old path rather than add a permanent parallel pipeline.

The larger tug of war is partly contractual. The accepted [retained preparation decision](../../../.agents/docs/planning/decisions/retained-prepare-publish.md) requires a bound setter to prepare text/Unicode/shaping/layout synchronously in Rust and adopt a revision before returning; queries must consume that revision. It explicitly defers an unrequested _serialized measurement sidecar_, and it does not prescribe a particular arena, rope, request codec or scan. Current `measure_paragraph_inner` always positions on setter preparation, which is the implementation's way to make glyph placements and later publication use the accepted revision; any different placement of that tail would need to prove that a query immediately after the setter and renderer publication do not recompute layout. Main and the published package defer changed setter work. For 1,024 independent setters followed by one scene publication, main stages cheap JS changes and makes one Rust frame update; HELD currently makes 1,024 semantic preparation transactions plus a later render publication. Coalescing those transactions _across_ calls would change the accepted immediate-observability contract, but removing redundant ingress, copying, branch work or sidecars _within_ each transaction does not. The measured dense gap is roughly 2–3 ms, not a proven semantic lower bound. Setter-only parity with a deferred setter is structurally difficult, yet no authenticated lower bound proves absolute parity impossible. A product decision to defer accepted preparation or redefine the required setter-only comparison would require human contract approval; this report does not propose it as an optimization wave.

## Where the designs fight

1. **Time of ownership.** Main's pending JS state can overwrite an old value before any Rust work. HELD's accepted setter must own a valid semantic revision immediately. That buys deterministic prepared reads and renderer rejection recovery but forces work for intermediate states. The accepted decision requires each setter to leave a queryable prepared revision; it still allows internal reuse and lazy serialization of unrequested sidecars. Deferral across setters or a second semantic executor would violate it.
2. **Granularity.** A persistent rope shares clean interior leaves in `O(log G + changed leaves)` structural work. Output columns are flat and host buffers are contiguous. Thus a sparse source edit can still copy clean `F`-column gaps, build old/new correspondence, or trigger one broad physical draw reduction. Tree sharing is not proof of end-to-end sparse complexity. Conversely, dense replacement via tree updates pays node/copy-on-write overhead with no reuse benefit.
3. **Semantic certainty.** Same-length ASCII reuse, packed UTF-16 discovery, safe shaping windows, and flow convergence are conditional. Arbitrary authored full-string replacement needs `Ω(U)` discovery/encoding; shaping may need context, bidi, fallback and line layout. A second JS Unicode parser or persistent speculative cache would duplicate authority and error behavior. The E3 short-run choice still invokes the same HarfRust path and must preserve cold output.
4. **Producer to consumer.** Setter preparation produces positioned masks and unpublished owner IDs. Gather consumes those masks, emits `PlanGlyph` plus field columns, and ordered compilation consumes old/new scope. A broad one-draw batch can require `Ω(G)` instance/summary reduction even if only one source owner changed. The renderer then uploads physical ranges; Three's one min/max upload span and TypeGPU's bounded range count can broaden cost further. Optimizing a producer without proving downstream scope is a common false win.
5. **Locality versus lifetime.** Packed UTF-16/SWAR discovery and SoA fields favor sequential scans; rope metadata and Arc cloning favor retained snapshots, rollback and sparse edits. E3's reset gather may improve sequential dense work but increases transient allocation churn. Cache/TLB/GC effects are plausible, not established by profile labels, counters or source alone. A shipping same-input allocation/GC attribution would be needed to claim those mechanisms.
