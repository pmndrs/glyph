## Architectural answer

There are **two separate speed conflicts**. First, main defers semantic work for ordinary no-read setters, while HELD adopts a queryable semantic revision before each bound setter returns. Second, sparse retained data favors rope sharing and narrow dirty intervals, while the renderer ultimately needs canonical, ordered, contiguous physical bytes. The first conflict is a scheduling/contract difference. The second is a representation and traversal choice, and can be optimized without weakening synchronous setters. Their costs must not be conflated.

For **repeated overwrites of one paragraph**, main can replace several desired values before one publication; unless an intermediate value is queried, it can skip shaping/layout for that superseded value. HELD must make each accepted value queryable and report its error at that setter. No same-contract algorithm can skip that semantic obligation. For **one changed setter on each of 1,024 distinct labels**, both designs eventually must produce semantics for all 1,024 final labels. Main can marshal and execute one root frame; HELD performs 1,024 separate public validation, request encoding, Wasm crossings, Rust preflights, semantic commits, and ownership transitions before the frame. That difference is potentially reducible overhead, not proof that the core Unicode/shaping work is intrinsically larger. The current setter does **not** compile a renderer plan each time: `state.rs::measure_paragraph_inner` expressly excludes gather and plan compilation. `render-planner.ts::_updateText/#prepareTextCandidate` and `handle-state.ts::prepareParagraph` are the current call path; `state.rs::prepare_update_inner` is the later publication path. Pinned main `render-planner.ts::_updateText/#compileFrame/#queryTextRequest` holds desired/published text, sends final mutations at publication, and uses a speculative paragraph query on demand.

## What is cause, what remains hypothesis

**Source-established cause:** main can defer/coalesce superseded semantic revisions; HELD cannot under the synchronous setter contract. Main's one root frame also amortizes request/transaction overhead across distinct labels, while HELD does one paragraph transaction per setter. Current gather and ordered storage have separate coordinate systems: source glyphs include recordless rows, selected records have identity/program/strike metadata, and batch order can differ from source order. The compiler's indexed topology, physical runs, bindings and rollback need some mapping and overlapping old/new state. A literal forward-only stream cannot simply replace them. These are obligations, not an argument for E5's exact 20-byte locator representation.

**Observed cost substitution:** E5 deletes actual gathered writes but adds direct loads/locators and raises scoped memory; its complete dense timings regress. E6 removes repeated local view construction in that same branch, but has no latency result. The source supports the mechanism; it does not prove that E6 recovers the lost time. E3's separately preserved shared-layout experiment also showed adverse dense/sparse timing and allocation, but its different artifact and timing cannot be numerically pooled with E5.

**Unresolved:** how much of E2's roughly 3.1 ms 1,024-label p50 gap to main comes from per-set TS/wire/Wasm transactions, immutable semantic work, gather conversion, ordered physical work, renderer work, GC or clock. The E5 profile is for a different source and sampling perturbs elapsed time. No current E2-versus-main phase decomposition or structural lower-bound proof separates those terms. SIMD instruction presence is not dynamic utilization, and a SWAR/packed scan win cannot substitute for whole-operation evidence.

## Ranked coherent hybrid choices

1. **Default: one semantic owner, packed physical locality for dense, retained ranges for sparse.** Keep `ParagraphState::prepare` as the only Rust semantic executor and retain prepared revisions for every setter/read/split. At publication use one `CodecGatherWorkspace` packed SoA and the same `OrderedPlanCompiler`: full/cold or near-complete output uses its existing exact dense builder and contiguous codec/SIMD runs; narrow scopes use 32-record rope sharing, source/record correspondence and coalesced physical ranges. E2 is the measured latency control for this policy, and E4's small proven source-read deletion may be retained only as a named combination. This has the best whole-scope risk profile today and already combines the two locality regimes. **Delete** the E5/E6 direct candidate workspace, locator vectors, `DirectOperandSource`/direct codec arm, duplicated direct admission, threaded optional source parameters and metadata-only cache mode from *active* source if E6's complete matrix does not justify them; keep the authenticated whole variants recoverable. Do not retain two equivalent executors behind a speculative switch. Complexity is O(changed semantic work) per setter; publication is O(selected changed rows + emitted bytes) for sparse and O(all selected rows + physical bytes) for dense. Old accepted rope/buffer generations and in-flight renderer bytes remain owned until acceptance; packed candidate state stays transaction-scoped. The cost is still full packed gathered fields on dense frames, but E5 proves removing those writes by itself can be worse.

2. **Next potential gain: narrow *existing-wire* setter ingress inside the same semantic transaction.** For a bound text-only replacement with unchanged style/geometry/identity, encode the already validated, package-owned mutation directly into the existing request arena layout, then call the same `measureParagraph` ABI and `ParagraphState::prepare`. Keep the generic `PlannerFrameUpdate` path for style, geometry, lifecycle and mixed edits. A dedicated writer may share the canonical header/text layout helpers; it must not introduce a second Rust preparation algorithm, a new public bulk operation, or skip caller-authored text/range/fault checks. Its deletion target is the generic per-call object/array preparation and redundant traversal in `render-planner.ts::#prepareTextCandidate`, `frame-wire.ts::preparePlannerFrameUpdate/writePreparedPlannerFrameUpdate`, and `handle-state.ts::#writeFrameRequest`, **only where exact source counters prove they are repeated**. The current frame writer already writes directly to Wasm, so a mere new wrapper or copied wire encoder is not a gain. Treat this as a conditional implementation wave after fixed E6 and a count/phase probe on E2/E4. Expected benefit is proportional to distinct setter count, potentially relevant to dense 512/1,024 and unchanged ingress; it cannot avoid Unicode/shape/flow for accepted changes. Risk is duplicate wire policy and changed error precedence; require one schema owner, byte-exact request oracle, same throw site and source-line deletion in the generic branch. No new persistent cache or memory peak is needed. If source inspection cannot identify actual repeat work large enough to target, do **not** implement this wave.

3. **Research option: bounded physical-order SoA tiles.** Keep the existing indexed `PlanGlyph`/source mapping and ordered compiler authority, but gather operands for each physical four-lane codec run into one small stack/scratch SoA tile and execute the existing scalar/SIMD interpreter on that tile. This could preserve packed locality while avoiding full gathered-field materialization; unlike E5's per-operand indirect getter, it pays source indirection once per tile. It must replace full gathered fields and the direct candidate machinery, not coexist as a third path. However source/record mapping, strike selection, unused declared-field error order, old/new overlap, 0–3 tails and batch reorder still need proof; any per-tile scatter may exceed saved writes. Complexity remains O(selected rows + active operands + physical bytes), with bounded O(tile fields) scratch but likely a retained row map. This is **not ready to implement** from current evidence. Prototype only after an exact producer/consumer work ledger names removable full-field traffic and shows the same physical run can consume tiles without a second codec interpreter or a new storage format.

4. **Different product contract: explicit bulk setter transaction.** One public bulk call could accept/prepare a whole batch synchronously and amortize ingress like main. It cannot retroactively make each existing individual setter's intermediate revision queryable or throw at that setter while skipping its work. It is therefore a separate API/benchmark comparison, outside this plan and not a hidden parity technique.

The **chosen next-wave brief** is conditional, not another local guess: finish the frozen E6 fixed-policy matrix first. If E6 wins selected complete operations against E2 with acceptable dense/sparse tails, size and memory, isolate which structural path produced the gain before retaining a narrowly gated direct mode; if not, return active policy to the E2/E4 packed+sparse hybrid and preserve E5/E6 as named correct variants. Then measure/counter-split the exact 1,024-distinct-label callback into setter ingress/wire, Rust semantic stages, gather/ordered codec, host publication and GC on authenticated controls. Count request bytes/allocations/Wasm entries, owner visits, Unicode/shape/positioned rows, actual gathered reads/writes, mapped records, compared/emitted bytes and transaction peak. Select the narrow existing-wire ingress only if it demonstrably deletes a repeated cost in the same operation; otherwise investigate the next largest measured owner without layering more branches. No 5% admission floor: evaluate unrounded block estimates/CIs, absolute p50/p95, all adverse and favorable rows, exclusions and clocks, and preserve correct inconclusive whole variants.

## Correctness, falsification and the structural-limit test

The independent oracle must compare every accepted setter with a cold engine for text, Unicode/bidi/shape/flow/position, stable IDs, measurement, borrow, carets/selections and an independently owned split that survives sibling edit/disposal. After publication compare exact selected records, physical byte plan, ordering/batches, host patch payload and rendered browser pixels on authenticated package installs. Exercise no-read overwrite, interleaved reads, same-value sets, long/unsafe Unicode boundaries, 0–3 SIMD tails, recordless glyphs, strikes/resources/unused codec inputs, decorations, zero masks, sparse and full intervals, count changes, reorders, allocation/overflow/fault, aborted encode, renderer rejection/checkpoint, stale borrows and in-flight generations. The cold engine is an output oracle, not a new production executor.

The proposed hybrid is disconfirmed if expected producer/consumer work is not actually removed; if E6 or a later candidate worsens dense against E2/main/published without a defensible family benefit; if sparse/query/copy gains or p95 collapse; if the same wire byte/error order and cold semantic/physical output do not hold; or if size/peak memory erases a small elapsed gain. Package/native/ABI/minimum-peer and CPU recovery receipts are narrower than browser/hero, full payload/layout and whole-app physical memory; close those on the final exact artifact. A nominal favorable CI in a related 145-row suite is a signal to preserve and test, not a causal proof.

A **structural limit** would require more than repeated failed local variants: under the same synchronous public operations, obtain per-set semantic-stage counts and a validated minimal same-contract executor cost on the exact distinct-label and repeated-overwrite fixtures; verify no unrelated owner work, duplicate validation/encoding, avoidable full-row conversion or excess physical bytes remain; establish a lower bound from required Unicode/shaping/layout and canonical renderer output with enough timing uncertainty to compare against main; and show independent correct representations approach that bound without size/memory regressions. The current evidence does not do that. The week of attempts says local gather/write removal is insufficient and that some old deferred advantage is real; it does **not** show Glyph is trapped or that a coherent contract-preserving hybrid cannot reach parity.
