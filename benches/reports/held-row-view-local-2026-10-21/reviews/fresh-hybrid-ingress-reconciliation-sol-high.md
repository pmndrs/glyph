# Fresh hybrid ingress reconciliation

21 October 2026. Read-only follow-up to `fresh-hybrid-performance-landscape-sol-high.md`; that report remains byte-exact. No build, benchmark, counter run, profile, source or Git change was made while the E6 fixed-policy matrix runs. **Decision: retire its ranked narrow existing-wire setter-ingress option as an implementation brief.** The current source and prior authenticated Bitmap audit identify no material safe ingress path to delete. The E6 matrix, when terminal, can alter the whole-variant choice but cannot itself make a duplicate encoder a justified architecture.

## Why the proposed ingress cut fails the source gate

The actual Bitmap 1,024-label callback changes one ten-unit plain string per label (`alpha NNNN` ↔ `bravo NNNN`) and publishes once. `three/text.ts` validates the public string and stages the frozen desired state; `configured-handle.ts` already recognizes reusable plain text and forwards `{text}` without full font/material/transform rebinding; `render-planner.ts::_updateText` already takes `textOnlyUpdate`, shares existing lease ownership through `forkResolvedTextWithText`, uses count-based aggregate limits and emits one full-span text mutation with empty style/geometry arrays. `#prepareTextCandidate` then invokes the existing `PlanTransport.prepareParagraph` and adopts the prepared semantic revision. The older independent ingress audit traced this exact route, including public surrogate errors, `PostCommitError`, renderer rejection, lease ownership and failure recovery. It found only unpriced constant-work Three/configured envelopes and repeated small guards, not a whole duplicate preparation path. E6 changes ten Rust files and does not change these TS/wire call sites.

`frame-wire.ts::preparePlannerFrameUpdate` sizes the **canonical existing ABI** sections and holds scratch for the synchronous write. `handle-state.ts::#writeFrameRequest` reuses that scratch, checks/reserves the retained request arena, rebinds a `Uint8Array`/`DataView` only when memory/pointer/length changes, then calls `writePreparedPlannerFrameUpdate` directly on Wasm memory. It does not allocate a final per-setter wire buffer. The writer's `bytes.fill(0)` covers reserved/padding/unused fields under the parser's canonical request contract; section offsets, checked arithmetic, UTF-16 payload writing and result fault/extent handling remain necessary. My earlier suggestion to encode a text-only request directly into the **same layout** would add a second schema writer or merely rename the existing writer. Removing the prepared descriptor's duplicate array references, as `plain-text-ingress-wave-advice.md` suggests conditionally, is a small O(1) descriptor cut, not a credible dense 2–3 ms wave. It can be considered during an already justified cleanup, not as the next performance architecture.

The apparent duplicate UTF-16 scans are not a safe deletion: Three's paired-surrogate check gives a public setter error and exact offset; Rust validates the independently callable ABI batch before semantic writes, then decodes into owned candidate text. Nor is there a second Unicode analysis to remove: Rust transfers its preflight candidate to preparation. Same-length text also maintains an inactive text/ID mirror for the next setter. The earlier audit found no repeated style/geometry serialization, full lease rebind, root-size aggregate scan or sibling-rank walk on this callback. A Three→configured private shortcut could skip `coreTextState`/presentation/snapshot envelopes only under a strict current-state/presentation/order/rejection gate, but it creates another cross-owner entry with error and lifetime proof. No statement-level evidence prices the deletion, and the current configured plain-text path already removes its largest generic work. This is **not ready** as a source-supported implementation. The E2 profile's JS self samples under `_updateText`, `#stage`, frame preparation and header writing are whole-function diagnostic samples, not removable elapsed cost.

## Evidence that arrived after the old audit

The original `independent-ingress-audit.md` correctly said actual Bitmap native semantic/allocator counts were then missing. They are **no longer missing in the same way**. The authenticated package capture/replay now reproduces 6,157 events, 4,099 results and 1,977,392 result bytes through the real request/font/codec producers and Rust parsers. The E6 `bitmap-native-replay/native-work-ledger.json` already reports both warm directions separately. Each has 1,024 HarfRust calls over 10,240 UTF-16 units, 1,024 full cluster builds and 10,240 full cluster glyph visits, 1,024 recomposed flow lines, 10,240 run-local glyph visits, 1,024 shape scratch arena moves/10,240 moved glyphs, and 10,240 newly positioned glyph rows. The later publication makes **zero** HarfRust calls, gathers 10,240 source rows and selects 9,216 actual Bitmap rows. Thus another generic "capture actual Bitmap counts" request would repeat completed work. Native counts are not phase latency, JS/GC or a proof that each semantic row is removable.

The current `state.rs::short_inter_label_assignments_use_incremental_shape_and_match_cold_output` adds a narrower Inter-font fact: for both alpha→bravo and bravo→alpha, the reconciled short edit takes an incremental-shape entry but ends with one `[0,10)` HarfRust window, one ten-unit call, zero old-shape glyph copies and one full cluster build; cold output matches. It observes only the **final** window. The earlier `short-dense-shape-scope-advice.md` correctly refuses to assume the unchanged space/digit suffix is a shaping-safe splice. HarfRust `UNSAFE_TO_CONCAT` old and newly shaped boundary flags, fallback and run topology own that decision. The current test's Inter TTF path and the package Bitmap font/binding are related but not interchangeable; the authenticated Bitmap replay establishes work totals, not the exact first attempted splice reason.

After the E6 full matrix reaches a terminal, source/authenticated-result verdict, the next unresolved owner is **Rust short-label semantic scope**, especially why five changed letters lead to ten shaped units, ten cluster visits and ten newly positioned rows per label. This is a question, not a selected suffix-reuse patch. The bounded next evidence action is to extend the existing test-only actual-Bitmap replay observation, using its already captured request/font/codec bytes, to record for both warm directions: reconciled `[0,5)` edit; old run/fallback topology; old glyph cluster and `UNSAFE_TO_CONCAT` flags at candidate offsets 5–9; the first window from `build_sparse_shape_windows`; whether `prepare_incremental_shape_scope` rejects it due to a new unsafe boundary, glyph-zero/fallback or another named guard; and the candidate new flags at that attempted end. Existing aggregate HarfRust/cluster/flow/position and publication counts are the baseline; do not request them again.

If neither warm Bitmap direction has a boundary certified safe by **both** old and new HarfRust answers before offset 10, retire short suffix-shape reuse for this cohort. Then the next owner question is full-cluster/flow/position work under unchanged suffix semantics, which needs an independent state-equality/dependency proof before any source edit. If an early boundary is safe yet the executor still shapes to 10, identify the exact extra guard or range-builder expansion and propose a correction inside the **one** existing shaping executor. Require cold semantic/ID/measurement/split and exact downstream physical/browser output, mixed Unicode/ligature/kerning/RTL/fallback errors, transaction rollback and the fixed seven-family matrix before admitting it. A safe five-unit shape window alone would not prove a whole-operation win or remove full layout work.

**Implementation readiness now: none for ingress, none for physical-order tiles, and none yet for suffix shaping.** Preserve E6 and E2/E4/E5 identities, await the one already-running fixed-policy E6 matrix, then answer the specific old/new concat-boundary question only if the matrix leaves dense parity open and root chooses a semantic-scope wave. The completed Bitmap ledger already rules out a theory that publication repeats HarfRust work and rules in substantial setter-side shape/cluster/flow/position work. It does not establish a contract lower bound or prove that a new fast lane can remove any of it.
