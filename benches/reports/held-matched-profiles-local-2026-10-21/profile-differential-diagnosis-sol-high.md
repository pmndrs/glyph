# Matched CPU profile diagnosis: dense Bitmap publication

## Decision-relevant finding

The main-to-held difference is primarily a **phase and ownership change**, not one slow gather function. Main records 1,024 text assignments and prepares them in the scene publication. E2–E6 and V3 synchronously prepare each paragraph during its assignment so an immediate `measure()` or `glyphs()` can see the new state; scene publication then gathers, compiles, and applies the prepared state. In the first matched raw call trees, main's setter subtree has 110.876 ms of exclusive sampled time and its publication subtree 1,019.374 ms. E4 has 953.551 ms in setters and 457.411 ms in publication. A reverse-order repeat confirms the phase migration, but changes the apparent arm timing rank and inflates different arms. None of these two noisy passes establishes a causal total-latency ranking. Summing marginal p50s or overlapping inclusive stacks would misstate this comparison.

V3's full-frontier range adapter removes owner-range iteration in the native diagnostic, but it does **not** remove the per-source callback, retained-rope traversal, field update, or later plan/renderer work. Its matched capture has a very unstable p95 and long profiler sampling gaps, so it does not establish a causal latency regression from the adapter. It also does not establish a latency win. Do not make V3 the next performance wave.

## Exact work by owner and phase

Main's 110.876 ms setter subtree is JS only in this capture: 68.88 ms in `internal/render-planner.js`, 37.21 ms in `three/text.js`, and 4.79 ms in `configured-handle.js`. Its expensive preparation is inside the 1,019.374 ms publication subtree, including named HarfRust self 203.37 ms, gather 74.87 ms, positioning 83.75 ms, clusters 40.58 ms, flow 45.63 ms, render-plan 31.29 ms, and JS source files including `render-planner.js` 68.04 ms and `layout-query-view.js` 34.33 ms. These are disjoint self-frame classifications, not overlapping inclusive totals. The old source at `4e25a96a:packages/glyph/src/internal/render-planner.ts` `_updateText` records a dirty desired text and makes a later query or publication do the preparation.

E4's 953.551 ms setter subtree has 237.03 ms named HarfRust self, 99.09 ms cluster code, 105.25 ms positioning code, 39.67 ms flow code, and 122.34 ms other `state` functions. Its JS self includes `render-planner.js` 98.33 ms, `three/text.js` 68.13 ms, `frame-wire.js` 48.08 ms, and `handle-state.js` 18.08 ms. Concrete named setter frames include `validate_planner_inputs` 42.502 ms/32 samples, `ParagraphState::prepare_clusters` 25.752 ms, `ParagraphState::prepare_positioned` 33.126 ms, and `ParagraphState::commit_all` 17.542 ms. The current `render-planner.ts` `_updateText` and `#prepareTextCandidate` synchronously call `PlanTransport.prepareParagraph`; `measure()` reads prepared state. `#prepareTextCandidate` already omits measurement serialization when no measurement has been requested; the timed case issues no reads. `frame-wire.ts` prepares an exact package-owned request, and `handle-state.ts` writes it **directly into the retained Wasm request arena**. There is no intermediate wire-buffer copy to delete.

E4's 457.411 ms publication subtree still contains 104.04 ms named gather self, 28.37 ms ordered-plan code, 68.00 ms other state, 97.58 ms Three JS, and 54.29 ms internal JS. Its named `retained_rope::update_ordered_node<GatherSource, OwnerRanges>` costs 35.001 ms/25 samples, `CodecGatherWorkspace::update_fields` 33.917 ms/25, `OrderedRanges::advance_to<OwnerRanges>` 12.500 ms/9, and the owner iterator 10.125 ms/7. Renderer and final output work remain after preparation: `command-buffer-renderer.js` 52.96 ms, transform synchronization 12.04 ms, placement-slot preparation 18.291 ms. Main and E4 compile different Rust implementations; compare semantic groups and original node IDs, not raw mangled names across hashes.

### Semantic work moved versus work actually repeated

The 1,024 final labels are distinct, so each owner needs one new shape, cluster map, flow, and positioned output. Main's `prepare_update_inner` (old `state.rs:1381`) walks the owner set in one publication transaction and calls `ParagraphState::prepare` per changed paragraph. E4's `measure_paragraph_inner` (current `state.rs:1378–1550`) calls that preparation once for the one owner in each setter. At publication, `prepare_update_inner` builds `order_sort_scratch` only from current semantic spans and pending preparation IDs (`state.rs:2946`); the setters already committed the semantic candidates, so the 1,024 unpublished IDs do not re-enter `ParagraphState::prepare`. This is **phase migration, not a second shaping pass**. The measured old/new cluster and positioning self totals (first capture main 40.6/83.8 ms versus E4 99.1/105.3 ms) do not prove increased semantic operations: the Rust implementations differ, and the reverse capture moves those totals with system variability. In that repeat, main publication has 27.6 ms named cluster and 97.8 ms named positioning self under the same name filter, while E4 setters have 100.3 and 127.8 ms. The cluster name filter is narrower than the earlier file-category total, so these are diagnostic examples, not a single normalized difference.

The source identifies **transaction work that really occurs more often**. E4 checks codec/revisions/lifecycle, runs `validate_planner_inputs`, routes the one owner through `prepare_semantic_inputs`, takes/returns preflight scratch, and admits the owner for publication once per setter (`state.rs:1378–1550`), instead of one root transaction holding all 1,024 changes. `validate_planner_inputs` validates the authored text and retained style topology, then preflights a candidate (`state.rs:6206–6395`). Preparation adopts that candidate's pending text/Unicode buffers (`state.rs:4392–4482`, `:4617–4639`); it does **not** rebuild text and Unicode from scratch after preflight. For equal-length edits, `commit_text` copies changed units and IDs back into the reusable pending mirror (`state.rs:4585–4615`), but old main does the same (`4e25a96a:state.rs:3496`); that copy is not a new E4-only cost. There is no demonstrated extra allocation per changed glyph or duplicate HarfRust call.

Publication _does_ visit every unpublished owner again in `commit_paragraphs(true)` (`state.rs:3880–3925`). `RetainedParagraph::commit_preparation(true)` clears the publication-dirty flag, calls `commit_all`, and marks the positioned output published (`state.rs:4017–4030`). Because the setter already committed each stage, the second `commit_all` has no prepared semantic candidate to swap, but it still invokes eleven stage commit methods and cleanup checks for each owner (`state.rs:4294–4306`). This is a source-backed deletion/fusion target: publish the already committed state and clear its flag without the redundant stage-commit walk, while retaining the existing path for any owner with pending preparation. The first E4 capture samples only 7.0 ms publication self in `commit_all` across 80 callbacks, however, so this change alone cannot close the gap.

The cluster and positioning implementations changed independently of scheduling. E4's `prepare_clusters` adds cluster-mapping invalidation and a full-source-run branch that chooses the full builder instead of the old topology-stable source-run rebuild (`state.rs:5271–5350` versus old `:4134–4210`); the held positioning builder adds retained-line correspondence and recomposed-line ranges (`positioning.rs:557–710` versus old `:557–700`). The profile has no per-owner branch counts for this exact fixture, so it cannot say whether either route executed or which semantic work became cheaper or dearer. A narrow exact-fixture counter for full-build versus incremental cluster admissions and retained versus recomposed positioned lines is the decisive follow-up **if** the no-op transaction deletion fails; optimizing those algorithms now would be an unsupported causal bet.

The V3 range helper at `state.rs:2723` proves all owners' old gather ranges are contiguous and all current source intervals are dirty, then passes one `0..end` interval into `codec_gather.rs:719`. The native diagnostic for its separate 1,024 × 10 fixture reports one full-frontier mode, two full-range iterator calls, zero owner-range calls, 10,240 source visits, 20,480 ordered-rope record visits, 5,120 copied rope records, and 40,960 emitted bytes per cycle. That diagnostic confirms V3 removes the **range iterator**. Its profile still attributes 77.914 ms/49 publication samples to `retained_rope::update_ordered_node<GatherSource, RetainedRanges>` (7.6% of the V3 publication subtree) and 61.084 ms/42 to `CodecGatherWorkspace::update_fields`. E4's corresponding rope frame is 35.001 ms/25 (7.7% of its publication subtree). The percentages are descriptive: the V3 capture is slower across unchanged semantic code, so its absolute delta cannot be attributed to the adapter. `retained_rope.rs:350`/`:1360` still traverses and reconstructs changed tree leaves; `codec_gather.rs:749` still advances owner and record cursors inside the source callback. The native 10-character diagnostic and profiled 9-character scene are distinct workloads; do not carry the 10,240 count into the profiled scene.

## Why the later variants did not close the whole callback gap

These secondary captures use the same named profile workflow but E2/E3/E5 are one capture each. E3's publication avoids the E4 retained-source hotspot by returning to fresh `gather_fields` (73.4 ms self) plus `append_from` (19.5 ms); work was shifted to full field gathering. E5's direct operand path lowers the reported gather bucket but adds `DirectRowContext::f32` 74.9 ms, `DirectRowContext::u32` 32.5 ms, `build_direct_candidate` 34.3 ms, and codec `execute_program` 50.8 ms, all publication self. E6's first capture has `DirectRowView::f32` 47.9 ms, candidate construction 30.3 ms, and codec execution 40.4 ms. The setter subtrees remain 764–823 ms sampled for E2/E3/E5/E6 in that pass. E6's reverse-order repeat has p50 15.840 versus 14.737 ms originally, confirming that these small apparent ranking differences are not robust. These results do not show that a single biggest Rust frame caused their whole-callback outcomes.

## Next coherent wave and its limit

The most defensible **internal** wave is a bounded deletion of repeated transaction scaffolding while keeping preparation synchronous. First, split publication acknowledgement of an already committed owner from the no-op eleven-stage `commit_all` walk (`state.rs:3880–3925`, `:4017–4030`, `:4294–4306`), retaining that walk for genuinely pending stages. Next, fuse the producer-proven single-owner text validation, route, and candidate adoption inside the _existing_ `measure_paragraph_inner` (`state.rs:1378–1550`, `:3015`, `:6206`) so the authored text is checked once and the same preflight candidate is consumed; preserve the general parser/validation path for lifecycle, style, geometry, multiple-owner, and forged raw ABI inputs. Finally, reduce per-call generic frame setup at `render-planner.ts:1234` and `frame-wire.ts:276` while retaining the direct arena writer and fallible pointer/length/capacity checks. This is an implementor brief for one measured wave, not authorization to bypass safety checks. The proof burden is immediate same-label ticker→quote→ticker query parity, exact native Bitmap and cold-output equivalence, failure recovery, order/split behavior, and published-package render parity. Do not cache a speculative future shape or change the public API.

Scope the fast path as one branch inside the existing transaction and wire writer, not a parallel executor or persistent second representation. Its candidate would be proportional to one owner's short input, while the unavoidable total preparation remains proportional to all 1,024 changed owners and 9,216 final glyphs; publication still walks the output it must emit. The `PlannerFrameUpdate` and its scratch slices are borrowed only through the synchronous arena write (`handle-state.ts:1655`); the Rust preflight candidate remains transaction-owned until adoption or discard. A faster path must preserve these lifetimes and failure rollback rather than storing a borrowed request or result pointer. V3's separate 10,240-row native diagnostic already reports one successful codec run and 2,560 SIMD-eligible four-row groups; its `codec::execute_program` work still exists. Changing SoA layout or adding another SIMD kernel has no demonstrated whole-callback case in these profiles.

This is a **candidate experiment, not a predicted win**. In the first E4 capture the individually named `validate_planner_inputs` self frame is 42.502 ms over 80 callbacks; all setter `frame-wire.js` is 48.08 ms; publication `commit_all` is 7.0 ms. Even an impossible deletion of those whole frames would save about 1.22 sampled ms per callback. Their necessary portions cannot simply be erased, and the repeat changes their sampled weights. HarfRust GPOS/substitution, cluster and positioned reconstruction for 1,024 final distinct values remain. No source or profile evidence establishes that the new synchronous path does _more_ semantic preparation than main for this fixture; the demonstrated increase is repeated transaction setup and publication acknowledgement. A wider redesign would need independent evidence that it can remove additional accepted work; the current profiles do not justify a claimed published win. Stop the old plan of making another narrow gather/range adapter the primary fix.

## Capture quality and unresolved work

V3 has 39 profile `timeDeltas` above 5 ms totaling about 467 ms; 38 are clustered in the middle four of eight equal-sample windows. Main has one such interval, the initial inspector `post`; E4 has that start interval plus two late 7.5 ms gaps. No raw V3 node has `deoptReason`. The V3 p95 148.512 ms and mean 39.342 ms describe that actual run, but the profile cannot identify whether scheduler contention, code generation, GC, or product work caused the gaps. A separate process snapshot after the captures showed other CPU-intensive work; it is contextual evidence, not proof of interference during V3. GC frames and anonymous/minified JS stay separately reported; neither GC causality nor cache misses, branch behavior, or hardware utilization follow from these V8 samples. One-capture E4/V3 absolute function deltas are not robust enough to set a new implementation target. The decisive next counter for the proposed fixed-cost wave is **per-callback exclusive time in single-owner preflight + frame encoding + publication no-op commit, paired with the existing accepted-output oracle**, rather than another generic stage total or a guessed count of owner ranges.
