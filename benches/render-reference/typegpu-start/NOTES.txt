Captures of the direct TypeGPU renderer (@pmndrs/glyph/typegpu) at the start of the parity and batching work
(branch experiments/sil-typegpu, cut from sil-green-4), 832x600, Chrome 149 headless, WebGPU on Metal.

Written and compared by `pnpm scripts run benchmark:typegpu-parity` (benches/scripts/verify-typegpu-parity.mts,
page benches/src/typegpu-parity-proof.ts). The same run compares every scene with the Three MSDF path drawn at the
same camera into an 8-bit linear target.

Starting result against Three at 8/255: one 1, fx 6, fx-outline 6, fx-shadow 1, fx-both 6, devanagari 4 pixels over
(all on cell edges the Three path trims away), fx-plain, fx-persp and labels 0. Bitmap is compared with its own
capture only: the Three path snaps bitmap quads to the pixel grid and this renderer does not.

Correction (2026-11-24): Three does not snap Bitmap quads by default (`pixelSnapping` is opt-in) and neither proof
enables it. The Bitmap scene differs from Three in 29,588 pixels over 8/255 because this renderer's 16 px line does
not match Three's 16 px Inter strike glyph for glyph; bitmap.png records that output. It stays compared with this
capture only until the TypeGPU defect is fixed.

Fixed (2026-11-25): the cause was filtering, not strike selection. Both renderers received byte-identical glyph lanes
and strike pages; Three samples the page through a linear sampler and this renderer loaded the nearest texel. It now
samples linearly and the Bitmap scene equals Three exactly (0 pixels differ). bitmap.png was not re-taken: it still
records the nearest-texel output and differs from the current render in 29,588 pixels over 8/255, every one of which
is now within tolerance of Three, which the harness accepts as a change towards Three. The scene is held to Three with
no pixel over the tolerance, like every other scene.
